## #14 — GO

Обе мои находки закрыты по существу, а не формально.

- **P2-A (PATH).** `typeset -gr PATH="/usr/bin:/bin:/usr/sbin:/sbin"` стоит во
  всех пяти root-исполняемых врапперах: `p4g-agent-phase-b0-install`,
  `-control`, `-publish`, `-acceptance`,
  `p4g-agent-remote-sync-attestation-publish`. Проверка не текстовая:
  `tests/host/phase-b0.test.js:759-765` кладёт в hostile-каталог `git`,
  возвращающий `exit 93`, подставляет его первым в PATH и требует, чтобы
  инсталлятор отработал успешно — то есть доказывает использование системного
  бинаря.
- **P3 (ротация логов).** Ротация вынесена из `.finally()` внутрь
  launchd-verified колбэка **до** провайдерских и бэкап-мутаций; комментарий в
  коде дословно называет мой сценарий («must never turn one successful snapshot
  into a five-minute KeepAlive loop»). Теперь отказ ротации означает отсутствие
  снапшота, а не переписывание успешного бэкапа в неуспех. Класс закрыт
  структурно.

Оговорка, не блокирующая: заявка «rotation before mutation» дополнительно
проверяется `toContain` по тексту модуля. Поведенческого теста нового порядка
нет — стоит добавить, но сама правка верна.

## #16 — NO-GO: два P1, контур неисполним на реальном хосте

Врапперы — единственный установленный путь: `ACCEPTANCE_BIN` и
`REMOTE_SYNC_BIN` (`phase-b0-acceptance.mjs:44-45`) указывают на
`/usr/local/var/p4g/swipe-agents/bin/…`, а не на `.mjs`. Я скопировал оба
враппера, снял только гейты личности и подал ровно ту argv, которую формирует
код.

### P1-1. `provider-probe` не принимается враппером → bootstrap гарантированно сносит хост

`phase-b0-acceptance.mjs:1555` вызывает `runJsonAsRunner(REMOTE_SYNC_BIN,
["provider-probe"])`. В `p4g-agent-remote-sync` case-блок содержит ветки
`check|init|seed-backup|restore-drill|quarantine-corrupt-head`, `backup`,
`scheduled-backup`, `verify-window`, `attest` — и всё. Команда добавлена только
в `parseArgs` модуля (`phase-b0-remote-sync.mjs`), во враппер — нет.

Исполнено:
```
wrap/p4g-agent-remote-sync provider-probe
  → usage: p4g-agent-remote-sync <check|init|seed-backup|backup|restore-drill|
    quarantine-corrupt-head|verify-window …|attest>        (ветка *) → exit 2)
```

Последствие: `p4g-agent-phase-b0-control bootstrap` поднимает все три демона,
ставит `BOOTSTRAP_IN_PROGRESS=1` и только затем зовёт `"$ACCEPTANCE_BIN" start`
→ `runner_verification_failed` → EXIT-trap `fail_closed_jobs` выгружает джобы,
дизейблит метки и удаляет live plists. Это **ровно та форма отказа**, которую
P2-J объявлен закрывшим; добавленный anchor-гейт её не ловит, потому что отказ
теперь другой. Bootstrap не может завершиться успешно ни разу.

Фикс: `provider-probe) (( $# == 0 )) || exit 2 ;;` в case и в usage-строку.

### P1-2. `rollback-store-state` приклеен не к той ветке враппера → квитанция отката недостижима

`phase-b0-acceptance.mjs:1816` вызывает
`["rollback-store-state", "--observed-at", observedAt]`; модуль это принимает
(`:1889`). Враппер `p4g-agent-phase-b0-acceptance` сгруппировал
`audit|rollback-store-state)` и требует `$2 == "--window-end"`, тогда как
соседняя ветка `rollback-receipt)` требует правильный `--observed-at`.

Исполнено:
```
wrap/p4g-agent-phase-b0-acceptance rollback-store-state --observed-at <ts>
  → usage …                                                      (exit 2)
контроль: wrap/p4g-agent-phase-b0-acceptance audit --window-end <ts>
  → проходит case-блок и упирается уже в гейт p4g_runner
```
Контроль подтверждает, что отвергаются именно аргументы, а не мой стенд.

Последствие: `control disable` доходит до `storeInspector`, получает exit 2 —
но к этому моменту все три джобы уже выгружены и `enabled:false` уже
опубликован. Типизированная квитанция отката не публикуется **никогда** и
доделать её нечем. Путь, которым закрывали P2-H, мёртв целиком; рунбук
описывает поведение, которого нет.

Фикс: отдельная ветка `rollback-store-state)` с `--observed-at`.

### P2 по #16 (из адверсариального прохода, мной не воспроизводились)

- **Аудит base-A1 стал слепым к незрелым ранам.** Предикат переведён на
  `grace_deadline_ts <= endMs`; при `graceMultiple=2` и суточном интервале
  grace бэкап-рана = start+48ч ≥ длины окна, поэтому зависший `scheduled`/
  `started` ран не попадает ни в `runStates`, ни в `missedRuns` (событие
  `missed` созревает уже вне окна). Аудит зелёный там, где до фикса был
  `base_a1_run_state_incomplete`. Прямая регрессия от фикса моего же P3.
- **`liveRuntimeLease` понижен до самозаявления runner'а.** Раньше root сам
  открывал store; теперь принимает булево поле из JSON того самого runner'а,
  которого отключают, а независимо проверяет только `launchctl print` и `ps` —
  неистёкший claim мёртвого PID процессом не виден по определению.
- **Операторская аттестация dead-man обязана уложиться в 5 минут после конца
  окна**, иначе `deadman_window_failed`, а `windowEnd` уже вморожен в
  root-evidence. Практически это вынуждает вписывать не то время, когда
  оператор действительно смотрел UI, — что подрывает ровно ту семантику
  человеческого гейта, ради которой P2-G сужали.
- **Поверхность позднего отказа bootstrap выросла**: `start` теперь делает
  preflight + два HTTPS к B2 + `systemsetup -getusingnetworktime` +
  `captureLaunchd`, и всё это после подъёма джоб. Недоступность B2 или иной
  формат вывода `systemsetup` сносят хост тем же трапом.

## #15 — NO-GO: исходный P1 закрыт, но тем же фиксом открыт эквивалент

### Что закрыто (проверено мной исполнением)

`git archive` удалён полностью; материализация идёт обходом графа объектов через
`/usr/bin/git cat-file` с пересчётом SHA-1 до использования байтов. Я собрал
отравленный репозиторий и прогнал новый экстрактор:

```
контроль (git archive, те же env):  b.txt исчез, a.txt = "PWNED", фильтр исполнился
новый extractTrackedSource:         a.txt = "hello\n", b.txt на месте,
                                    sub/c.txt = "nested\n",
                                    FILTER_RAN создан экстрактором = false
убегающий симлинк:                  REFUSED release_candidate_symlink
```
`core.autocrlf true` тоже не сработал. `GIT_ATTR_NOSYSTEM=1` и
`GIT_NO_REPLACE_OBJECTS=1` присутствуют. Исходный канал закрыт по существу.

### P1-3. Билдер больше не проверяет байты кода, которым собирает

`assertExactSource` (`p4g-agent-phase-b0-release-candidate.mjs:126-138`) теперь
сверяет только `rev-parse HEAD`, а проверка чистоты worktree удалена — с
комментарием «Worktree bytes and status are deliberately irrelevant: the release
is materialized from the reviewed commit object, never from the checkout».

Для **содержимого релиза** это верно. Но сам билдер исполняется из worktree:
`SCRIPT_DIR = dirname(fileURLToPath(import.meta.url))`,
`SOURCE_ROOT = resolve(SCRIPT_DIR, "../..")` (`:32-33`). То есть код,
выполняющий материализацию, теперь не проверяется ничем. Асимметрия введена
именно этим фиксом и резко контрастирует с соседями, которые проверку сохранили:
`p4g-agent-phase-b0-install:59` (`refusing: source worktree is dirty`) и
`p4g-agent-phase-b0-release-install.mjs:103` (`release_install_dirty_source`).

Воспроизведено end-to-end: патч билдера в worktree без коммита → билдер не
отказывает и выдаёт валидный v2-receipt с посторонним файлом в дереве →
`git checkout --` возвращает чистоту → инсталлятор **принимает** этот кандидат
по его же дайджесту. И главное: `buildManifestDigest`, `toolchain`,
`nativeArtifact`, `sourceTreeOid` у отравленной и чистой сборки **идентичны** —
расходится только `releaseTreeDigest`. Поскольку рунбук предписывает две сборки
тем же скриптом из того же чекаута, обязательный двойной билд снова
**подтверждает** отравленный дайджест, а не ловит его.

Это структурно тот же дефект, что исходный P1: детерминированный тампер,
невидимый для всех заявленных проверок идентичности, который ритуал
воспроизводимости легитимирует.

Фикс: вернуть отказ на грязные tracked-файлы (на детерминизм он больше не
влияет — только на аутентичность исполняемого кода) либо сверять байты
собственных модулей `host/phase-b0/*.mjs` с блобами из `sourceCommit` через уже
имеющийся `readGitObject` до начала сборки.

### P2 по #15

- **`dist/tests` едет в «production»-релиз.** `PRODUCTION_PRUNE_PATHS` =
  `[".github","docs","host","src","tests","tsconfig.json"]` — только исходники.
  `tsconfig.json` объявляет `include: ["src/**/*.ts","tests/**/*.ts"]`,
  `outDir: "dist"`, `rootDir: "."`, поэтому сборка кладёт `dist/tests/**`, и
  prune его не трогает: 225 файлов, 1.4 МБ — кодовая поверхность релиза
  удвоена. Среди пяти модулей, загружаемых без dev-зависимостей, —
  `dist/tests/helpers.js` с `makeHarness`, подставляющим `AGENTS_ACCEPTANCE=1`;
  это ровно та переменная, ради изоляции которой в `p4g-agent-unattended`
  стоит `env -i` с комментарием «env -i is the authority boundary». Тест
  (`phase-b0-release-candidate.test.js:222`) проверяет
  `existsSync(join(releaseRoot,"tests")) === false` и потому зелёный при живом
  `dist/tests`.
- **Ни один из 12 новых кодов отказа не покрыт тестом** (`release_candidate_
  gitlink|symlink|git_path|git_mode|git_tree|git_object_digest|
  git_path_collision|native_digest|native_archive|native_platform|toolchain`,
  плюс install-коды). Проход проверил четыре вручную — работают; но регресс
  любого CI не поймает.
- **Алгоритм tree-digest изменён без смены версии домена.**
  `phase-b0-host.mjs:566` теперь хеширует `"mode-ignored"` вместо режима, при
  этом доменный тег остался `agents.phase-b0-release-tree.v1` (`:532`). Само
  изменение обязательное (под пиннутым umask 0077 macOS создаёт симлинки
  `lrwx------`, инсталлятор копирует их под своим umask и без `lchmod` — старый
  дайджест ломал бы каждый `--apply-release`), но две несовместимые функции
  теперь носят одну версию: любой ранее выписанный activation-receipt даст
  `release_tree_digest_mismatch` без диагностируемой причины. Нужен `.v2`.

## Системная причина, общая для обоих P1 этого раунда

Оба дефекта #16 невидимы для 492 зелёных тестов, потому что во **всех** восьми
эффектных поверхностях внешние границы инжектируются: `providerProbe`,
`storeInspector`, `spawn`, `kill` подменяются заглушками, и ни один тест ни разу
не подаёт фактическую командную строку во враппер. Проверки вида
`expect(wrapper).toContain(...)` смотрят наличие подстроки, а не приём
аргументов. P1-3 в #15 — та же болезнь с другой стороны: удалили проверку,
которая одна и отвечала за аутентичность исполняемого кода, а тесты этого не
заметили, потому что проверяют результат сборки, а не её происхождение.

Пока не появится тест, который прогоняет **реальную argv каждого вызова
`runJsonAsRunner` через настоящий враппер**, и пока билдер не проверяет
собственные байты, этот класс будет воспроизводиться каждый раунд. Рекомендую
сделать это условием следующей передачи на ревью, а не просто ещё одним пунктом
диспозиции.
