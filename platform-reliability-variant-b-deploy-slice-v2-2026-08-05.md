не умеет. Фаза 5 обязательна в обоих случаях.

**Фаза 3 упала после стейджинга env, но до/во время deploy.** Компенсация env
живёт только внутри `_set_release_env_with_cas`; при обрыве снаружи она не
отрабатывает. Проверить фактические `PLATFORM_*` на сервисе перед любой
повторной попыткой.

**preDeploy упал после `alembic upgrade`.** Известное свойство: база остаётся
на `0073`, квитанция не создаётся. Это не повод откатывать схему —
`operation=rollback` её и не трогает.

**Любой упавший cutover-прогон не оставляет квитанции.** Единственное
доказательство — логи прогона и ручной снимок состояния Render. Снимать сразу,
до любых новых действий.

## Пин исполняемого кода

Cutover исполняет workflow по ref диспатча, а environment не имеет branch
policy. Требования:

- `ref = master` при каждом cutover-dispatch;
- `master == 0e9e940` сверяется **перед каждым** из двух cutover-диспатчей;
- workflow и координатор побайтово неизменны **между** фазами 2 и 3;
- желательно завести branch policy на environment `production` — но это
  улучшение, не блокер.

## Выделено в отдельный пакет: сапёр в ростер

Бывший шаг 3.2 — не шаг. Фактический путь по `mechanic-onboarding.md:78-130`
проходит через два authority-контура: identity → canonical mapping manifest с
независимой проверкой → mapping dry-run → apply под однократным
`ENABLE_FEED_MAPPING_REGISTRY_OPS=true` → при новой family ещё ontology →
roster entries manifest → register dry-run и apply → activation dry-run → CAS
activation с точным текущим activation ID и дайджестом прод-манифеста →
`/session` и два перезапуска мини-аппа.

Пакет пишет R1-A, ревьюирует хаб-сессия. Он **не блокирует** деплой и
исполняется после фазы 4.
