# Независимое решение порядка: Gate C0 против R1-A cutover

- Дата: 03.08.2026. Reviewer: Claude (Fable 5). Запрос — PR #40,
  комментарий `5170863017`. Read-only; ничего не запускалось.

## Вердикт

**Предложенный порядок отклоняю. Рекомендую обратный: сначала Gate C0,
но с временной заморозкой `render.yaml` на master.**

Остановку preflight'а считаю правильной: конфликт реальный, и обнаружен он
до мутации, а не после.

## Что проверено

Расхождение подтверждаю. `render.yaml` на master действительно несёт полный
контракт R1-A: `dockerfilePath: ./Dockerfile.bake → ./Dockerfile` для web,
`preDeployCommand` с `python -m app.platform_release predeploy-env`, ключи
`PLATFORM_DATABASE_IDENTITY`, `PLATFORM_RELEASE_MANIFEST_B64/SHA256`,
`PLATFORM_DEPLOY_IDENTITY`, `PLATFORM_RELEASE_OPERATION`. В самом файле стоит
комментарий: «Activated only in the separately approved R1-A cutover. Until
then this branch is evidence, not a request to mutate the production
Blueprint.» Пересоздание Blueprint из master превращает это evidence в
request — вывод preflight'а верен.

Относительно relink-only: контракт Gate C (шаг 5) требует создания нового
Blueprint «from the exact same repo, branch and `render.yaml` path», а
инструмент сравнения жёстко ограничивает `sourceBranch` перечислением
`['master']`. То есть ветку подменить нельзя без правки и контракта, и
инструмента — это и есть тот «source-freeze/relink mechanism», который назван
альтернативой.

## Почему предложенный порядок не годится

**Первое, фактическое.** Формулировка «complete the separately rehearsed R1-A
cutover» описывает состояние, которого нет. Сегодняшний completion-аудит
R1-A говорит прямо: rehearsal доказателен только для графа `0070→0071` и
требует обновления для `0070→0073`; candidate-v3 ждёт отдельного GO; GitHub-
окружения `production` и репозиторных секретов релиза не существует вовсе.
То есть до cutover не один шаг, а минимум четыре операторских акта, каждый с
ревью между ними.

**Второе, и оно решающее.** Всё это время утёкший хук остаётся живым — а его
радиус только что вырос. Render подтвердил `hookCanInitiateBlueprintSync:
true`, и теперь синхронизация, инициированная хуком, предложит применить
контракт R1-A: смену Dockerfile, `preDeployCommand`, новые ключи. То есть
именно то, ради контроля чего и строятся четыре гейта, оказывается достижимо
в обход них. Предложенный порядок сохраняет это состояние на дни.

Радиус хука при этом **неизвестен**: провайдер не уточнил, применяет ли
инициированная хуком синхронизация изменения или только создаёт ожидающий
preview, а аудит использования хука Render не предоставил
(`providerSideActorAuditProvided: false`). Держать неограниченную экспозицию
открытой, добавляя гейты перед её закрытием, — неправильная сторона этого
незнания.

## Рекомендуемый порядок

1. **Временно заморозить `render.yaml` на master** — коммит, возвращающий
   `Dockerfile.bake`, убирающий `preDeployCommand` и ключи `PLATFORM_*`, то
   есть приводящий файл к содержимому, совпадающему с живой конфигурацией.
   Остальные 47 коммитов не трогаются: расхождение по коду не мешает
   relink-only, мешает только контракт деплоя.
2. **Провести Gate C0** обычным путём: preflight, приостановка обоих cron,
   900-секундное окно, удаление и пересоздание Blueprint из master.
   Relink-only соблюдается буквально — тот же репозиторий, та же ветка, тот
   же путь, и теперь то же содержимое. Ни контракт, ни инструмент сравнения
   править не нужно: перечисление `['master']` остаётся истинным.
3. **Вернуть контракт R1-A обратным коммитом** — он должен быть побайтово
   тем же, что сейчас на master, что делает пару коммитов тривиально
   проверяемой.
4. **Дальше R1-A своим чередом** на новом Blueprint: candidate-v3, свежий
   rehearsal `0070→0073`, подготовка окружения, пакет cutover, исполнение.

Цена — два механических коммита в `render.yaml`. Взамен экспозиция
закрывается первой, а не последней, и исчезает состояние, в котором чужая
синхронизация применяет неотревьюенный cutover.

## Чего я сознательно не рекомендую

Правку `sourceBranch` в инструменте ради заморозочной ветки. Она работает, но
стоит дороже: новый рецензируемый пакет, изменение принятого контракта и
расширение перечисления, которое сейчас служит защитой. Заморозка содержимого
даёт тот же результат, не трогая ни того, ни другого.

И отдельно: **не совмещать два операторских гейта в одном окне** — здесь я с
запросом полностью согласен. Даже при рекомендованном порядке C0 остаётся
relink-only, а R1-A — отдельным решением со своими доказательствами.

## Что удешевит решение

Один вопрос в уже открытый тред Render: **применяет ли синхронизация,
инициированная Sync Hook, изменения — или только создаёт ожидающий preview,
требующий Approve?** Если верно второе, радиус экспозиции резко уже, срочность
падает, и предложенный порядок становится защитимым. Пока ответа нет, я
исхожу из худшего прочтения.

Это ревью — evidence, не authority: ни C0, ни R1-A cutover им не
разрешаются.
