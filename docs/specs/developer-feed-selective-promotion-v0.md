# Proposal: selective promotion из dev-ленты

Статус: **QUEUED PROPOSAL — не implementation authority и не dispatch**.

Приоритет: не начинать реализацию до завершения текущей уборки Feed,
механик и ещё одной серии сложных/параллельных Telegram rework dogfood.
Этот документ сохраняет принятое продуктовое направление, но не блокирует
эти работы и не создаёт отдельного owner, heartbeat или review-цикла.

Связанный действующий контракт:
[lab-playable-release-fast-lane.md](lab-playable-release-fast-lane.md), §2.1.

## 1. Задача

Dev-лента должна позволять быстро проверять изменения только на операторе,
а затем отдельно продвигать выбранные версии более широкой аудитории.
Публикация одного объекта не должна неявно публиковать весь накопившийся dev.

Целевые аудитории:

```text
Только мне → Команда тестирует (опционально) → Доступно всем
```

Принятие dev-версии и публичная публикация — разные решения:

- dev-решение подтверждает, что exact версия подходит для дальнейшего
  наигрыша;
- promotion-решение подтверждает exact release plan, аудиторию и публичные
  последствия;
- ни dev-adoption, ни успешный dogfood не дают publication authority.

## 2. Продуктовая поверхность

Happy path находится **в клиенте платформы, внутри dev-ленты**, а не в
техническом Labs.

### 2.1 Общий экран

Верхний бейдж `Dev-лента · Только мне` становится нажимаемым. Он открывает
mobile-first bottom sheet или экран **Изменения dev-ленты**.

Экран показывает только объекты, у которых dev отличается от публичной
версии:

- механика и её exact dev/public версии;
- платформа Feed и её exact dev/public версии;
- текущая аудитория;
- человеческий статус и причина блокировки, если она есть;
- действия `Проверить`, `Доработать` и `Продвинуть`.

Labs остаётся поверхностью диагностики, evidence и истории попыток. Для
обычного продвижения оператор не должен открывать Labs, GitHub или терминал.

### 2.2 Контекстное действие

На карточке изменённой механики рядом с `Доработать механику` появляется
`Продвинуть…`. Это короткий вход в тот же server-owned promotion plan, а не
вторая реализация публикации.

Кнопка скрыта, когда dev и public совпадают. Она disabled с понятной причиной,
когда exact dev-head ещё не готов к promotion plan или имеет unresolved
`FAILED/NEEDS_HELP`.

## 3. Единица продвижения

По умолчанию одно действие продвигает **ровно один выбранный объект**:

1. exact версия одной механики;
2. exact версия платформенной оболочки;
3. явно показанный связанный пакет, только если зависимость доказана.

Публикация Marble Sort не затрагивает dev-версии Two Dots или Klondike.
Публикация платформы не публикует механики, которые видны только оператору.
Действия `Вылить весь dev` в v0 нет.

Если механика зависит от неопубликованной версии платформы, система не
подмешивает её молча. Promotion plan должен остановиться или показать точный
связанный пакет, например:

> Для публикации Two Dots требуется Platform `abc123`. Продвинуть оба
> изменения?

Каждая часть пакета сохраняет собственную identity, проверки и rollback/recall
границу.

## 4. Процедура

1. Оператор открывает `Изменения dev-ленты` или нажимает контекстное
   `Продвинуть…`.
2. Выбирает аудиторию: `Команда тестирует` либо `Доступно всем`.
3. Backend строит server-owned plan из **уже сыгранной exact dev-версии**:
   source, artifact, runtime, review binding, mapping/roster и platform
   identities. Mutable `latest` или случайный свежий `master` запрещены.
4. Dev-evidence переиспользуется. Повторяются только устаревшие проверки и
   добавляются гейты риска выбранной аудитории.
5. Telegram показывает человеческое резюме: что изменится, для кого, какие
   зависимости включены и что останется только в dev.
6. Одно content-bound подтверждение авторизует exact plan.
7. Система выполняет штатный rollout и возвращает `LIVE` либо typed
   `FAILED/NEEDS_HELP` с одним следующим шагом.

При любой ошибке текущая публичная версия остаётся неизменной, а dev-версия и
исходный feedback lineage сохраняются. Повторное создание правки с нуля не
требуется.

## 5. Гейты по аудитории

### Только мне

Всегда fail-closed остаются actor/auth binding, immutable digests, bounded
scope, secrets/schema/arbitrary-input защита, отсутствие публичной утечки,
focused technical gate и operator-visible acceptance assertion.

Gamefeel, полная device-матрица и широкая совместимость не должны задерживать
каждую мелкую итерацию exact-user dogfood.

### Команда тестирует

Добавляются cohort binding, отсутствие видимости вне команды, smoke на
поддерживаемых командных устройствах и понятный recall обратно в exact-user.

### Доступно всем

Добавляются только public-risk проверки:

- полная затронутая compatibility/regression matrix;
- public/guest и wider-device smoke;
- public roster/catalog/mapping impact;
- проверка соседних механик и платформенной оболочки;
- rollout/canary/recall readiness;
- review tier по реально затронутой backend/Feed/publication authority.

Эта строгость принадлежит переходу аудитории, а не каждой первоначальной
правке в dev-ленту.

## 6. Статусы в клиенте

Техническое состояние и аудитория отображаются отдельно. Минимальный набор
аудиторий:

- `Только мне` — синий/бирюзовый;
- `Команда тестирует` — фиолетовый;
- `Доступно всем` — зелёный.

Технические состояния (`Готово`, `В работе`, `Нужна помощь`, `Продвигается`)
не кодируются теми же цветами и не маскируют аудиторию. Например, объект может
быть `Только мне · Нужна помощь`, сохраняя исходный текст и причину.

## 7. Реализация после активации

Предлагаемая bounded-декомпозиция:

1. **Read-only inventory:** экран отличий dev/public и contextual entry без
   mutation authority.
2. **Exact promotion plan:** выбор аудитории, dependency closure, Telegram
   preview и content-bound authorization.
3. **Selective rollout:** promotion одной механики, затем отдельно платформы;
   typed terminal receipt и сохранение старого public при ошибке.

Перед реализацией необходимо обновить proposal измерениями новых
параллельных dogfood-тестов. Не строить generic environment manager, новый
workflow engine, task store, scheduler, merge queue или массовую публикацию.

## 8. Acceptance v0

- С телефона за два перехода видны все dev/public отличия.
- Одну механику можно продвинуть, не изменив остальные dev-объекты.
- Платформу можно продвинуть отдельно с явным предупреждением о глобальном
  влиянии.
- Неявная зависимость блокируется; явная показывается до подтверждения.
- Promotion использует exact сыгранные bytes и переиспользует свежие
  dev-evidence.
- Провал public gate не изменяет public и не удаляет dev-head.
- Публичная публикация требует одного exact Telegram confirmation и даёт
  проверяемый LIVE receipt.
- Labs не требуется для happy path.
