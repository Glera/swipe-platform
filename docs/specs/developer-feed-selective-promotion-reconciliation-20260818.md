# Reconciliation 18.08.2026: selective promotion v0 → v1

Статус: **FROZEN v1 CONTRACT (операторские решения 18.08.2026).**
Оператор подтвердил все три решения §D: (1) carrier = catalog/allocation,
builtin-механики мигрируют постепенно, dev-static не строится («А
подтверждаю»); (2) аудитория «Команда тестирует» отложена до появления
команды; (3) порядок реализации — сначала read-only «Изменения dev-ленты»,
затем promotion для marble-sort. #109 (статусы) строится поверх этого
контракта. v0-документ остаётся историческим входом.

## A. Что изменилось с 14.08 (факты)

1. **Условия активации v0 выполнены.** Уборка Feed/механик завершена;
   серия сложных/параллельных dogfood пройдена: 3 механики при capacity=2,
   параллельные rework-циклы, Klondike «замечание→LIVE» ≈ 5 мин, два
   полных круга платформенного intake (#134/#135 — 19 мин на круг).
2. **#108 закрыт.** «Доработать» существует и для механик, и для платформы
   с телефона; intake → GitHub Issue → прод — доказанная петля. Значит
   поверхность «Изменения dev-ленты» получает уже живые действия
   `Доработать` в обе стороны — v0 это только предполагал.
3. **S2a/#121 в рантайме.** Композер имеет lineage-aware presenter,
   честные статусы и close-семантику. §6 v0 (аудитория ≠ техсостояние)
   становится требованием к #109, а не частью этого контракта.
4. **S1 backend LIVE** (mobile review, флаги OFF): просмотр/приёмка
   кандидатов с телефона появится независимо от promotion-оси; экран
   «Изменения dev-ленты» и mobile-review не должны раздваивать статусную
   правду — оба читают одни server-owned identity.

## B. Ключевое расхождение v0 с реальностью доставки

v0 говорит про «dev отличается от public», но у builtin-механик
СЕГОДНЯ НЕТ носителя этой разницы: accept в fast lane публикует общие
байты в единственный static-деплой — «Только мне» для builtin физически
не существует (Klondike стал LIVE для всех в момент принятия).

Единственный существующий носитель оси аудитории — **catalog-контур**:
content-addressed runtime + per-user allocation + admission-ladder
`candidate → canary → published` + exact-user dogfood. Для marble-sort
эта машинерия уже построена (флаги открытия player-v2 пока OFF).

Следствие: «продвинуть механику» имеет два разных носителя, и строить
третий (параллельный dev-static или второй канал доставки builtin) —
запрещённый клон инфраструктуры.

## C. Реконсилированный v1 (предлагаемый)

1. **Carrier decision.** Ось аудитории живёт в catalog/allocation.
   Builtin-механики получают selective promotion не отдельным механизмом,
   а через миграцию в catalog-доставку (существующий roadmap открытия
   `capabilities.levelSeries` / player-v2). Никакого dev-static.
2. **V1 scope, реализуемый сейчас:**
   - **(a) Read-only «Изменения dev-ленты».** Экран/шит из бейджа
     дев-ленты: список объектов, где dev-identity ≠ public-identity,
     собранный из существующих server-owned источников (release registry,
     static `release.json`, rework lineage, catalog admission state).
     Никакой mutation authority. Это же — входная поверхность статусов
     для #109.
   - **(b) «Продвинуть…» для catalog-механик** = продуктовая обёртка над
     УЖЕ спроектированным promotion-binding TMA Approve и admission
     policy (известный runtime → published напрямую; новая граница →
     candidate→canary ladder). Ни одного нового publication-механизма.
   - **(c) Платформа (Feed shell)** в v1 остаётся global-on-deploy:
     оператор — единственный пользователь, «Только мне» для платформы
     сейчас тождественно проду. Отдельное продвижение платформы
     активируется вместе со вторым cohort'ом.
3. **Аудитории v1:** `Только мне` (catalog exact-user) и `Доступно всем`
   (published). `Команда тестирует` откладывается до существования
   команды — cohort binding нечем наполнить, а пустая аудитория в UI —
   ложь.
4. **Статусы:** контракт полей (аудитория, техсостояние, причина
   блокировки) фиксируется здесь; отрисовка и вся семантика цветов — #109.

## D. Три продуктовых решения оператора

1. **Carrier:** согласен ли, что ось аудитории = catalog/allocation, а
   builtin-механики мигрируют в catalog-доставку вместо постройки
   dev-static? (Это определяет всю дальнейшую механику.)
2. **Аудитории v1:** ок ли убрать «Команда тестирует» из v1 (вернётся
   с появлением команды)?
3. **Порядок:** сначала (a) read-only diff-экран — быстро и само по себе
   ценно, потом (b) promotion для marble-sort; или сразу (b)?

## E. Что НЕ делаем (усиление запретов v0)

- Никакого второго канала доставки builtin (dev-static, cohort-бандлы).
- Никакого «Вылить весь dev», массовой публикации, environment manager,
  workflow engine, нового task store/scheduler/merge queue.
- Promotion не создаёт новую publication authority: единственный
  публикационный акт — существующий content-bound TMA Approve.
- Ничего из этого документа не является implementation authority до
  операторских решений §D и заморозки v1.
