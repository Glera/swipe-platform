# Адверсариальное ревью: agents-operator-qa draft v1 (`swipe-backend@1d96f36`)

Дата: 2026-07-20. Ревьюер: внешняя линия (владелец agent-team ТЗ).

## Вердикт: архитектура верна; до GO — 3 P2 (все правятся текстом) + P3-россыпь

Что правильно и трогать не надо: новое полномочие объявлено честно и
обнесено правильно (только reply на явный вопрос, рендер шаблоном над
схемой, никаких инициативных постов); двухплоскостная схема facts/advisory
сохраняет существо старого запрета §11 структурой, а не добрым словом;
кураторская модель журнала (LLM никогда не пишет напрямую, типизировано,
версионировано, retired вместо стирания) — верный разрыв петли; квота без
спауна на отказе; shadow-first rollout за graduation A1; concurrency=1 и
общий бюджет §9 не размываются.

## P2 — до GO

### P2-1. Evidence в facts[] проверяется только схемой — сфабрикованные ссылки маскируют выдумку под данные
§5 требует «пункт без evidence не проходит схему», но schema-валидация
проверяет ПРИСУТСТВИЕ `{reportId, rowDigest | field}`, не их ИСТИННОСТЬ.
LLM может сослаться на несуществующий rowDigest или чужой reportId — и
«факт» пройдёт как факт. Это дыра ровно в том месте, которое
двухплоскостная схема защищает: выдумка с выдуманной ссылкой строже
маскируется, чем выдумка без ссылки. Фикс: валидатор обязан РАЗРЕШАТЬ
каждую evidence-ссылку против exact input manifest прогона (report/rows
там лежат побайтно — §4.4): неразрешимая ссылка = reject всего ответа
(fail-closed, не тихий downgrade). Тест: fake-LLM с фиктивным rowDigest →
reject.

### P2-2. Вторая петля обратной связи — K последних Q&A-пар — не признана в threat model
§3 разбирает петлю LLM→журнал→LLM (и правильно гейтит её оператором), но
§4.4.1 кладёт в контекст «до K последних Q&A-пар этого UTC-дня» — это
АВТОМАТИЧЕСКАЯ петля LLM→контекст→LLM без человека в разрыве, в тот же
день. Инъекция, пережившая валидатор в тексте ответа (валидатор режет
URL/императивы, но не любые инструкции), самореплицируется в следующие
прогоны дня. Фикс текстом: (а) признать петлю в §3; (б) Q&A-пары входят
тем же untrusted typed-блоком; (в) injection-корпус §9 получает класс
«инструкция в ПРЕДЫДУЩЕМ ОТВЕТЕ» (не только в вопросе и в инсайте);
(г) опционально — в контекст идут только вопросы + facts-плоскость
предыдущих ответов, без advisory (сужает канал репликации).

### P2-3. Анти-URL/анти-императив — блэклист, а рендер не обязан быть некликабельным
§3 обещает «LLM не может никуда направить оператора» силой value-scan.
Блэклист-сканирование обходится (гомоглифы, «t точка me слэш …»,
перефраз императива) — это best-effort, и по канону этого проекта такое
признаётся честно, а не продаётся как гарантия. Структурная же защита
дешёвая и не указана: рендер ответа обязан отправляться БЕЗ
Telegram-разметки (parse_mode отключён / полный escaping, preview
отключён) — тогда даже проскочивший сквозь скан URL/деп-линк остаётся
некликабельным текстом. Фикс: (а) §3 переформулировать value-scan как
best-effort слой; (б) специфицировать некликабельный рендер как
несущую защиту + тест «URL, обошедший скан, отрендерен инертно».

## P3 — по усмотрению (рекомендую 1–3 до GO)

1. **Fingerprint `qa:<hash вопроса+день>` без asker'а**: два допущенных
   пользователя с одинаковым вопросом в один день коллидируют — второй
   вопрос коалесцируется, reply уйдёт на первое сообщение. Либо включить
   asker user id (и classificationEventId уже в окне) в fingerprint, либо
   специфицировать семантику «одинаковый вопрос дня отвечается один раз»
   явно.
2. **Отказы сверх квоты не ограничены**: 11-й..N-й вопрос дня получают
   шаблонный reply каждый — скомпрометированный/зациклившийся допущенный
   аккаунт превращает отказы во flood delivery-контура. Bounded: например
   ≤3 отказ-reply в сутки, дальше terminal-классификация с audit без
   ответа (паттерн breaker).
3. **Каналы /ask**: «в любом из трёх прод-каналов» размывает дисциплину
   severity — Q&A-болтовня в incident-канале мешает его caps/тишине.
   Рекомендация: /ask принимается только в digest-канале (и test-чате в
   shadow); в других — вежливая terminal-классификация rejected_invalid.
4. **Reply-привязка /remember <n>**: специфицировать разрешение номера
   через reply message id → delivery → attempt → candidateInsights ТОГО
   ответа (не «последнего»), и отказ при reply не-на-ответ-бота.
5. **Видимость усечения журнала**: при >64KB старые активные записи молча
   выпадают из контекста — оператор считает их «в памяти». Одна строка в
   дневной сводке: «в контексте N из M активных инсайтов».
6. Голос/файлы → ignored: убедиться, что §12 terminal-классификация даёт
   audit-след (не молчаливый дроп) — вероятно уже так, зафиксировать.
