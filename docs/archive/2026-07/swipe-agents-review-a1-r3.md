### Подтверждено закрытым

- **№1 split-brain first-init — FIXED.** `tryCreateCurrent` = голый
  `symlinkSync` (EEXIST = проиграл), победитель читается `realpathSync`,
  удаление кандидата гейтится от коллизии имён; 20 worker-threads на
  SAB-барьере сходятся в один storeDir без остатков. Осиротевший кандидат
  без `authority.sqlite` не адоптируется.
- **№2 crash-safe миграция — FIXED в первичном инварианте.** Copy → publish →
  delete-legacy-последним; все crash-точки сходятся к «старая БД с событиями
  никогда не даёт активный 0-event store»; adopt отличает полный каталог
  безопасно по построению. Но hot-DB-гард порот — см. R3.1-1.
- **№3 band-деэскалация / слепой рестарт — FIXED (а)–(д).** Band читается из
  durable probe-события; поле аддитивно, legacy-события без metric дают
  консервативную задержку, не преждевременную деэскалацию; рестарт-тест

  class-only правила деградируют ровно к старому поведению.
- **№4a/№4b restore — FIXED.** Legacy-flat root требует `force`; стирание
  flat(+wal/shm+evidence) ПОСЛЕ flip — окна без единого store нет; кривой
  `fileName` отклоняется на входе до staging.
- **№5 backup promotion — FIXED в первичном требовании.** Evidence первым
  недеструктивным merge, DB-rename последним как единственный commit-marker;
  читатель игнорирует evidence-без-DB; re-run после сбоя проходит. Но два
  новых дефекта — R3.1-2/R3.1-3.
- **№6 реестр — исправлен в главном** (band 0/1/2, дельта 5 добавлена);

## R3.1 — до GO

### R3.1-1 (P2, введён фиксом №2): hot-DB проба не ловит idle-WAL-держателя — окно потери данных
`checkpointAndAssertNoHolder` (`src/store/data-root.ts:120-138`) полагается
на `BEGIN EXCLUSIVE` → BUSY. В WAL-режиме idle-соединение (нормальное
состояние живого рантайма между транзакциями) НЕ конфликтует с EXCLUSIVE.
Воспроизведено эмпирически: при открытом живом `Store` на flat-БД миграция
проходит (`MIGRATED=true FLAT_DELETED=true`) и `removeLegacyFlat` unlink'ает
файл из-под живого писателя — рантайм пишет в мёртвый inode, копия под
`current` этих записей не видит. Это ровно сценарий №2 (старый рантайм жив,
новый процесс инициализируется — та же multi-process семья, что №1). Ветка
отказа не покрыта ни одним тестом. Фикс: честный держатель-детект (например
`PRAGMA wal_checkpoint(RESTART)`+проверка busy, или lock-файл с O_EXCL и
liveness, или отказ мигрировать при существующих `-wal`/`-shm` с недавним
mtime) + тест с живым idle-соединением, падающий на текущем коде.

### R3.1-2 (P2, введён фиксом №5): опубликованное evidence не реверифицируется — усечённый файл публикуется навсегда
`cpSync(force:false)` merge (`src/backup/backup.ts:148`) неатомарен
по-файлово: crash посреди merge оставляет усечённый target-файл с полным
digest-именем; re-run видит «present» → пропускает → не чинит никогда.
Верификация гоняется по staged-дереву, опубликованное дерево не проверяется.
Тот же класс бага, что чинил №5, перенесён в merge-шаг. Фикс: после merge и
ДО DB-rename прогонять `verifyEvidence` против `targetEvidenceDir`
(digest-имя = само содержимое, проверка тривиальна) + тест с усечённым
pre-existing файлом.

### R3.1-3 (P2, тест): инъекция первого promotion-теста инертна под новым кодом
`backup-promotion.test.ts` арит `failAt:2` («второй rename»), но новый
happy-path делает ровно ОДИН `renameSync` (DB-commit; evidence теперь
cpSync) — инъекция никогда не срабатывает, ассерт условный
(`if (existsSync(dest))`) — тавтология. Red-then-green валиден только против
старого кода; текущий фикс crash-сценарием не покрыт. Фикс: инжектировать
сбой в cpSync-merge (это же покроет R3.1-2) и безусловные ассерты.

### R3.1-4 (P3, реестр): три неточности
(1) В amendment-чеклисте нет строки для дельты 5 (`probe-event.v1.metric`) —
чеклист и есть смысл реестра; (2) `missed_run` назван band-правилом, хотя
эмитит сырой счётчик consecutive-missed (совпадение порогов 1/2 случайно);
(3) `projection_drift` пропущен в списке band-правил, хотя подпадает под тот
же фикс.

## Замечания без блока (backlog)
- Осиротевшие кандидат-каталоги от crash до publish копятся до
  `pruneOldVersions`; adoption проверяет только `existsSync(STORE_FILE)` без
  integrity (сегодня недостижимо, хрупко к будущим правкам).
- `probeFiresAtOrAbove` считает одиночный in-band probe «сработавшим» для
  не-immediate правил — консервативная задержка деэскалации, безопасно.
