Что правильно и трогать не надо: единственный замороженный scope с возвратом
в ТЗ; секрет server-side, hash-only, показ один раз, префикс `agr1_`;

## P2 — правки ТЗ до GO

### P2-1. Ротация ломается об `name UNIQUE`
§3: `name TEXT UNIQUE` тотальный, отозванная строка имя не освобождает.
Первая же ротация `analyst-shadow-mac` = выпуск нового с ТЕМ ЖЕ именем →
конфликт UNIQUE. Либо оператор плодит имена (`-2`, `-3` — рвётся
непрерывность имени в receipts агентской стороны, где принципал пинится
`AGENTS_M2M_READ_PRINCIPAL`), либо ротация невозможна как описана.
Фикс в ТЗ: partial unique `ON (name) WHERE status='active'` — имя
переиспользуемо после отзыва, активный держатель всегда один.

### P2-2. 401 по неизвестному токену: не аудитируется и не лимитируется
§6 обещает аудит «на каждый машинный запрос», но перечисляет только
401-по-отозванному (у него есть principal по hash). Неизвестный токен не
даёт principal_id → строка невозможна (поле в схеме не помечено NULLABLE), и
per-principal rate limit к нему неприменим. Итог: спрей мусорных
`AgentsRead`-токенов — неограниченные и невидимые обращения к hash-lookup
(перебор 32-байтового секрета нереален, но это бесплатный неаудитируемый
DB-запрос на каждый анонимный запрос — DoS-поверхность, и слепое пятно
ровно в том аудите, ради которого таблица заведена). Фикс в ТЗ:
`principal_id NULLABLE` + строка для unknown-token 401 (endpoint, ts, без
principal) и плоский unauthenticated-лимит (глобальный или per-IP, N в
конфиге) на машинную схему до hash-lookup.

### P2-3. Хранилище rate limit не специфицировано — а от него зависит корректность N
§5 задаёт «N запросов/мин на принципала», не говоря, где живёт счётчик.
In-memory на multi-worker/multi-instance Render умножает N на число
процессов. В проекте уже есть атомарный Postgres-паттерн
(`rate_limits.consume_limit` + `usage_counters`), но он ключуется
`user_id FK users.id` — для UUID-принципала как есть не подходит. Фикс в
ТЗ: явная строка «лимит — атомарный Postgres-счётчик по паттерну
`usage_counters`, отдельная таблица с ключом principal_id» (окно/retry-after
переиспользуются).

### P2-4. Аудит 429 — амплификация под runaway-агентом
Threat model §2 сама называет runaway-цикл, а §6 требует строку на каждый
429 при «retention бессрочно (объём тривиален)». Зацикленный агент (или
атакующий с валидным токеном) на сотнях rps превращает append-only таблицу
в мусорную кучу, и каждый отклонённый запрос стоит INSERT — отклонение
дороже обслуживания. Фикс в ТЗ: 429-аудит коалесцируется — одна строка на
принципала на окно лимита с счётчиком подавленных (паттерн breaker'а из
agent-team §10); success/401 остаются по-строчно.

## P3 — по желанию / в acceptance

1. **Слепое пятно скомпрометированного токена на чужих ручках**: машинная
   схема на не-разрешённой ручке даёт 401 от `tma`-зависимости БЕЗ
   аудит-следа (следствие решения «без глобального middleware» — решение
   правильное). Вписать в §6 одной строкой как принятое ограничение.
2. **Runbook — обязательный deliverable, не упомянут**: agent-team §12
   требует issuance/rotation/revoke/compromise-response как обязательный
   раздел runbook. Добавить в §8/§9 пункт «обновление runbook-a1 (или
   отдельный runbook-m2m)»: ротация по расписанию (рекомендация, не TTL),
   compromise-response = revoke → выпуск → замена env → проверка аудита за
   окно компрометации.
3. **Гигиена ручного acceptance**: §8 «curl'ом читает три ручки» — токен в
   argv попадает в shell history/ps. Прописать `curl -H @file` или env-var.
   Заодно: ответ `/issue` пометить `Cache-Control: no-store`.
4. **Scope как CHECK**: «замороженный enum» сделать структурным — DB CHECK
   `scope IN ('content-analytics:read')`, чтобы новая строка enum'а
   физически требовала миграции (= ревью ТЗ), а не UPDATE.

Мелочь без действия: RFC 7235 считает имя auth-схемы case-insensitive —
в реализации сравнивать `AgentsRead` без учёта регистра (или явно
задокументировать точное совпадение); отсутствие TTL при наличии
rotation/revocation соответствует §2 agent-team — сознательно ок.
