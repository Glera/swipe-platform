## 1. Правило-вариант для копии (exact)

### 1.1 Доска

- Поле `N×N`, разбитое ровно на `N` цветных регионов (связных).
- Измеренный диапазон в наигрыше: **`N ∈ {4,5,6,7}`**; `4×4` только на уровнях
  1–2 (туториал). Рабочее ядро — `5×5`–`7×7`.
  `queensgames.org` заявляет `8×8` как «Daily board» — то есть жанровый
  потолок публично уходит до 8.
- Регионы **не равновелики и не полимино-регулярны**: измеренные размеры при
  `N=6` — например `[1,1,5,8,10,11]`, при `N=7` — `[1,1,6,7,9,12,13]`.
  Один регион почти всегда «губка» на 25–45% доски.

### 1.2 Три ограничения (verbatim, три независимых источника)

Экранные чипы `meowdoku.app` (постоянно видны над доской):

1. `1 cat in each color region`
2. `1 cat in every row and column`
3. `Cats can't touch, even diagonally`

`queensgames.org` (hero): «Place one queen in every row, column, and colored
region. No two queens may touch – not even diagonally. Pure deduction. No
guessing.»

Dossier (стор-описание `com.nebula.zoodoku`): один зверь на регион, без
совпадений строк/колонок, без диагональных касаний, unique solution,
«no numbers, no math».

Формально: разместить ровно `N` фигур так, что
- ∀ строки: ровно одна фигура;
- ∀ столбца: ровно одна фигура;
- ∀ региона: ровно одна фигура;
- ∀ пары фигур: `max(|Δrow|, |Δcol|) ≥ 2` (запрет хода короля — **это НЕ полная
  диагональ ферзя**; дальние диагонали разрешены).

Последний пункт — единственное место, где жанр расходится с классическими
`N-ферзями`, и `queensgames.org` сам это проговаривает: «Classic N-Queens …
only rows and columns matter. Queens Game adds colored regions, so every cell
belongs to a region that must also contain exactly one queen.»

### 1.3 Инвариант единственности

**Подтверждён измерением, не декларацией.** Я прогнал собственный
exhaustive-солвер (backtracking по строкам с ранним отсечением на 2-м решении)
по 16 подряд идущим уровням: **16/16 имеют ровно одно решение.**

### 1.4 Marking-модель — три разные, выбирать осознанно

Измерено покликово (состояние читалось из DOM, не с картинки):

**A. `meowdoku.app` (фан-билд, ближе всего к мобильному казуалу)**
- одиночный тап по пустой клетке → **X-метка** (`icon_mark.png`);
- одиночный тап по X → пусто (X тогглится, а не идёт дальше по циклу);
- **двойной тап** → фигура (из любого состояния);
- одиночный тап по фигуре → пусто;
- **drag красит X** вдоль протяжки, **пропуская занятые клетки** (проверено:
  протяжка через клетку с котом оставила её нетронутой);
- **auto-X отсутствует.** Постановка фигуры не помечает ни строку, ни столбец,
  ни регион, ни диагонали — вся бухгалтерия ручная. Именно поэтому X-слой
  вообще нужен.

**B. `queensgames.org`**
- одиночный тап тогглит **саму фигуру** (пусто ↔ корона). **X-состояния нет
  вообще.** Для `6×6` это играется, для `8×8` — почти наверняка нет.

**C. LinkedIn Queens (по dossier/родословной, first-hand не проверено)**
- 1 тап = X, 2 тапа = ферзь, drag = покраска X. То есть A — это её наследник.

**Рекомендация для нашей ленты:** модель A без drag (см. 5.4 — drag конфликтует
со swipe), плюс **опциональный auto-X как настройка**, потому что ручная
бухгалтерия — главный источник длины сессии.

### 1.5 Немедленная обратная связь по конфликту

- Постановка в конфликт **разрешена и не является fail**.
- `meowdoku.app`: **обе** конфликтующие фигуры переключаются на «dizzy»-спрайт
  (закрученные глаза) мгновенно; клетка не подсвечивается. Крестики при этом
  не расставляются.
- `queensgames.org`: клетка целиком заливается тёмно-красным, корона краснеет.
- Ни в одном билде конфликт не блокирует ход и не отнимает ресурс.

### 1.6 Таймера нет, fail-состояния нет

- `meowdoku.app`: таймера нет, счётчика жизней нет, ходы не ограничены,
  «проиграть» нельзя в принципе. Победа — единственное терминальное состояние.
- `queensgames.org`: таймер **есть**, стартует по первому взаимодействию, идёт
  вверх, рядом leaderboard. Это **social/speedrun-рамка**, а не часть правила.

Вывод для копии: **таймер — свойство поверхности, а не механики.** Линия
LinkedIn (web/social) = таймер + шеринг времени; линия мобильного казуала
(Meowdoku/Zoodoku) = без таймера + сердца.

### 1.7 Сердца vs хинты — решение для нашей ленты

**Рекомендую хинты, сердца НЕ брать.** Основания:

1. Механически здесь **нет fail-состояния**. Сердца в мобильном оригинале
   вводят наказание за *неверную постановку*, то есть превращают
   correctness-oracle в валюту. Это прямо противоречит заявленному ядру
   «pure deduction, no guessing» и портит именно ту петлю, ради которой
   механику берут.
2. Сердца — это retention/monetization-контур с серверным состоянием и
   таймером восполнения. У платформы Stage 0: legacy economy/rewards
   выключены, `capabilities.levelSeries=false`, живой аудитории нет. Сердца
   некуда монетизировать и незачем хранить.
3. В ленте выход из уровня — свайп. Экран «жизни кончились, ждите» в ленте
   не удерживает, а отдаёт слот соседней карточке.

Хинт-слой ставить **обучающим** (см. 3.4), лимит — параметр конфига
(предлагаю: без лимита в dev-ленте, bounded — когда появится экономика).

### 2.2 Что из этого следует (ключевые ручки сложности)

1. **Сложность двухосевая, и `N` — не главная ось.**
   Формат id — `level-<L>-<N>x<N>-r<STRATEGY>-idx<I>-seed<S>` — прямо выносит
   `strategy` в идентичность уровня. `r1` (уровни 1–7) целиком решается
   forced-singles: **ноль нетривиальных шагов**. `r2` (с уровня 8) стопорится
   на 2–4 фигурах из `N` и требует **ровно одного нового класса техники**
   (confinement), после чего добирается до конца без ветвления.
   То есть тир — это «какой техникой требуется владеть», а не «насколько
   большая доска». Для нашей фабрики это ровно та классификация, которую
   солвер умеет выдавать бесплатно.

2. **Эскалация тира — по поведению, а не по номеру уровня.**
   В `queens:game-progress:v1` живут `currentStrategy`, `consecutiveCleanWins`,
   `consecutiveFails`, `consecutiveRetryLevels`, `retryTrackingStrategy`,
   `lastLevelCleanWin`. Переход `r1 → r2` произошёл ровно после того, как
   `consecutiveCleanWins` дошёл до 2. Понижение тира я не проверял (играл
   чисто) — **в unresolved**.

3. **Размер доски — пила, а не лестница.**
   `4,4,5,5,6,5,5,6,6,7,6,6,6,6,7,6`. После каждого «пика» (первый `6×6`,
   первый `7×7`) идёт откат вниз. Это осознанный retention-приём: пик даётся
   как достижение, а не как новая норма.

4. **Генератор всегда сажает 1–3 синглтон-региона.** Во всех 15 seed-уровнях
   минимальный регион = 1. Синглтон — это бесплатная стартовая фигура, то есть
   гарантированная точка входа и **потолок сложности**.

5. **Уровень 10 — из другого банка.** Единственный id **без `seed`**
   (`idx44`), единственный с `minRegion = 3` и **нулём синглтонов**,
   единственный, не берущийся моими двумя техниками (2 ветвления). В прогрессе
   рядом лежит пустой ключ `lkModProgress` (гипотеза: «lk» = LinkedIn-подобный
   импортированный банк). Вывод: **сеяный генератор даёт лёгкие уровни, а
   «настоящая» сложность приходит из ручного/импортированного банка.** Это
   прямое предупреждение нашей фабрике.

6. **Givens как онбординг-костыль.** Уровни 1–10 стартуют с одной уже
   поставленной фигурой; с уровня 11 givens = 0. Дешёвый и честный приём.

7. **Счётчик в HUD подсказывает правильность.** Проверено разделяющим
   экспериментом: конфликт-фри, но **не** решенческая постановка счётчик **не**
   увеличивает; решенческая — увеличивает. То есть `1/4` значит «одна фигура
   стоит там, где надо», а не «одна поставлена». Это заметное смягчение
   относительно «pure deduction»: игрок получает soft-oracle. Для нашей ленты
   я бы **брал нейтральный счётчик** (поставлено/N), а correctness-счётчик
   держал как опцию для первых уровней.

### 2.4 Длина сессии — что измерено и что оценка

**Измерено точно (tap-экономика):**
минимум взаимодействий на уровень = `N` двойных тапов = `2N` тапов
(`10` для `5×5`, `12` для `6×6`, `14` для `7×7`), **плюс** ручные X — а их
столько, сколько игрок сам решит поставить, потому что auto-X нет.

**Оценка (НЕ измерение):** `r1`-уровни `4×4`–`5×5` — 20–40 с;
`r2` `6×6` — 45–90 с; `7×7` из «жёсткого» банка — единицы минут.
Обоснование: `r1` не содержит ни одного нетривиального шага (доказано
анализатором), поэтому время = чтение доски + `2N` тапов; `r2` добавляет ровно
один класс дедукции.

Честная реальная кривая времени человека **не измерена** — см. раздел 7.
Опубликованных чисел по этому титулу не нашёл; leaderboard `queensgames.org`
засеян и как источник времени негоден.

## 3. Генерация и солвер

### 3.1 Формулировка exact cover

Задача точно ложится в exact cover / CSP:

- **Переменные:** `N` фигур, по одной на строку (переменная `row_i` = номер
  столбца) — это сразу снимает ограничение строк.
- **Ограничения-покрытия (exact):** каждый столбец покрыт ровно один раз;
  каждый регион покрыт ровно один раз.
- **Ограничение-исключение (не exact-cover, а пара-запрет):**
  `max(|Δrow|,|Δcol|) ≥ 2` для всех пар. В DLX это добавляется как вторичные
  колонки/пре-фильтр смежности; в CSP — как бинарный constraint между
  соседними строками (достаточно проверять `|row_i − row_{i+1}| ≥ 2`, потому
  что для `|Δrow| ≥ 2` запрет не действует).

Практический вывод: **достаточно перебора по строкам с проверкой трёх условий**
— мой солвер на 16 досках до `7×7` отрабатывал мгновенно; DLX не нужен до
`N ≈ 10+`.

Кодирование для человеко-читаемого дедукт-солвера (нужного для тиров
сложности): юниты = `N` строк + `N` столбцов + `N` регионов, техники —
`naked single` → `locked candidates (region↔line)` → пары/тройки → ветвление.
Уровень получает тир по **самой сильной технике, без которой он не решается**.
Это ровно то, что делает наблюдаемый `r1/r2`.

### 3.2 Рецепт генерации (dossier + подтверждено наблюдением)

1. Случайная валидная расстановка `N` фигур (placement-first): по строкам, с
   проверкой столбцов и запрета соседства. Это и есть будущее решение.
2. Выращивание регионов вокруг фигур: каждая фигура — семя своего региона,
   дальше BFS/случайный рост, пока все клетки не розданы; регион остаётся
   связным.
3. **Доказательство единственности исчерпывающим перебором**; поле с >1
   решением выбрасывается.
4. **Классификация тира** дедукт-солвером (3.1). Отбрасывать не только
   неоднозначные, но и «пустые» — те, что решаются вообще без нетривиального
   шага, если целевой тир выше `r1`.

Наблюдение, которое рецепт уточняет: референс **специально оставляет 1–3
региона размера 1**. Это не побочный эффект роста — это ручка. Хочешь легче —
больше синглтонов; хочешь сложнее — `minRegion ≥ 2..3` (как в их «жёстком»
банке на уровне 10).

### 3.3 Оценка сложности генератора для нашей фабрики

**Низкая — это самый дешёвый генератор из всей партии R0.**

- Состояние уровня сериализуется как `N` + карта регионов (`N²` малых целых) —
  для `7×7` это 49 чисел. Никаких траекторий, физики, порядков выдачи.
- Солвер и генератор — один и тот же перебор; «честность» уровня доказуема
  тотально, а не сэмплированием. Сравнить с кластером 2 (physics smash), где
  solver-verifiable не достигается в принципе.
- Ожидаемая стоимость: **генерируемо, `levels.ts`-авторинг не нужен** и даже
  вреден. Единственное, что стоит авторить руками — «жёсткий» банк для верхних
  тиров, если дедукт-солвер не сможет надёжно производить `branch = 0` уровни
  с `minRegion ≥ 3` (референс, судя по уровню 10, именно так и поступил).
- Риск-номер один: **формально валидный ≠ честный для человека** — та же
  формулировка, что уже записана в `docs/mechanics` для triple-tile. Гейт:
  уровень допускается, только если дедукт-солвер закрывает его **без
  ветвления** на заявленном тире.

### 3.4 Хинт-ладдер референса (готовая спецификация)

Фан-сайт описывает свой хинт-конвейер, и я подтвердил срабатывание на доске:
хинт сначала проверяет **ошибки игрока** (фигуры не по решению; X-метки,
блокирующие решение; взаимно конфликтующие фигуры), затем — есть ли
**форсированная фигура**, и только затем предлагает **где ставить X**.

Наблюдённое срабатывание на `7×7`: нижняя шторка «💡 **Mark These Cells** —
These cells are blocked by existing cat placements. Mark them with X.», доска
притушена, подсвечены **ровно 8 клеток**: вся строка занятой фигуры (6) плюс
две клетки её столбца сверху вниз. Полное замыкание элиминации было бы шире —
значит батч **ограничен** (гипотеза: cap = 8). Точное правило отбора — в
unresolved.

Это очень хороший образец: хинт **не выдаёт ответ**, он выполняет за игрока
следующий шаг бухгалтерии. Для нашей ленты — брать именно такую форму.

## 5. Feed-fit

### 5.1 Портрет

**✓ Родной.** Проверено съёмкой в `390×844`: доска — центрированный квадрат,
правила-чипы сверху, три круглые кнопки снизу. На `7×7` доска занимает ~44% по
высоте — то есть в нативной вёрстке ленты помещается с большим запасом, включая
верхнюю safe area. Скриншоты `01`/`04`/`05` в этой же папке.

### 5.2 Сессия

Минимум `2N` тапов (`10–14`). Оценка 20–90 с в зависимости от тира
(см. 2.4) — попадает в целевой коридор ленты ≤60 с на `N ≤ 6` и `r1–r2`.
**Рычаг длины сессии — не размер доски, а auto-X:** без него игрок тратит
основное время на ручную бухгалтерию. Если нужен более короткий раунд — включать
auto-X, а не уменьшать `N`.

### 5.3 Автоплей-тизер 3–5 с

Детерминированно берётся из solver-trace, без записи геймплея:

- `0.0–0.6 с` — доска проявляется, цветные регионы видны сразу (читается без
  текста: «поле поделено на цветные куски»);
- `0.6–2.0 с` — три фигуры встают подряд с шагом ~0.45 с, каждая гасит свою
  строку/столбец волной X — **правило показано, а не рассказано**;
- `2.0–2.8 с` — намеренно ставится конфликтная фигура: обе фигуры мгновенно
  переходят в «ошибочное» состояние → это единственный кадр, который объясняет
  ограничение соседства;
- `2.8–3.4 с` — конфликтная снимается, встаёт верная;
- `3.4–4.2 с` — последняя фигура + вспышка победы.

Сильные стороны: причинность видна без звука и без текста; кадр конфликта даёт
«я понял правило» за один взгляд. Слабая: это не физическое движение, поэтому
автоплей проигрывает по «сочности» кластеру Bus Jam — берём читаемостью, не
зрелищем.

### 5.4 Takeover-совместимость

- **Тап-модель безопасна:** одиночный и двойной тап не конфликтуют с
  вертикальным свайпом ленты.
- ⚠ **Drag-покраска X конфликтует со свайпом ленты** — вертикальная протяжка по
  доске неотличима от жеста прокрутки. Решение: в feed-варианте либо убрать
  drag совсем, либо разрешить только горизонтальную протяжку внутри строки, либо
  включать drag только после перехвата (takeover) карточки.
- Уровень полностью «паузится» бесплатно: состояние — статическая сетка,
  никакой симуляции, `onPause/onResume` тривиальны, поле переживает
  BFCache/перезаход без потерь (референс это и делает — прогресс восстановился
  после полной перезагрузки).

### 5.5 Место в каталоге классов

`docs/mechanics/README.md` держит семейство **«Logic grid»** с единственным
классом **«Sudoku»**, строка сводной матрицы:
`Sudoku | Feed 2 | Раунд 2 | Генерация 5 | Reuse 3 | S–M | риск: «длинная
статичная сессия» | приоритет 11`.

Кандидат — **новый класс внутри того же семейства**, не подмена Sudoku
(таксономия прямо запрещает незаметную подмену класса). Предлагаемая строка,
целиком опирающаяся на измерения выше:

`Constraint placement (регионы + запрет соседства) | Feed 4–5 | Раунд 4–5 |
Генерация 5 | Reuse 3 | S–M | риск: «формально валидный ≠ честный», различимость
палитры регионов | приоритет — операторский`

Что именно снимает записанное возражение «длинная статичная сессия»:
нет ввода цифр, нет notes-режима, нет `9×9`, раунд `2N` тапов, и главное —
**доска меняется на каждом ходу видимо** (конфликт-состояния, X-волна), тогда
как Sudoku визуально статичен. Возражение относилось к правилу Sudoku, а не к
семейству — это фиксировалось и в shortlist.

Reuse честно ставлю `3`, а не выше: с живыми классами (`marble-sort-swipe`,
pins, merge) переиспользуется shell/аналитика/чест-контур, но не игровой
рендер — здесь своя сеточная доска.

## 6. Граница trade dress

### 6.1 Public domain / свободно

- Сама расстановка `N` не атакующих фигур — задача о ферзях, ей ~180 лет
  (Bezzel 1848, Gauss); никем не удерживается.
- Комбинация «регионы + одна фигура на регион + запрет хода короля» —
  это Star Battle (`⋆`-battle, `1★`-вариант), известный печатный жанр
  логических головоломок задолго до LinkedIn; правила головоломки как таковые
  не охраняются авторским правом.
- Требование единственности решения, X-разметка, undo/restart/hint — общие
  жанровые конвенции.

### 6.2 НЕ копировать

- **Названия:** `Meowdoku`, `Zoodoku`, `Queens`, `Queens Game`. Слово
  «Queens» в связке с этой головоломкой прочно ассоциировано с LinkedIn —
  своё имя обязательно; «*doku» в названии тоже не брать (чужая линейка и
  вдобавок вводит в заблуждение — это не Sudoku).
- **Арт:** кошачьи/зоопарковые спрайты референса (`normal_cat_sprites.png`,
  `dizzy_cat_sprites.png`), включая сам гэг «закрученные глаза как индикатор
  конфликта» — это выразительное решение, а не правило; берём свой тип
  индикации.
- **Палитра регионов** референса (я снял их точные значения только чтобы
  зафиксировать «вот это не использовать»: жёлтый `#E3BA46`, лаванда
  `#9179D1`, роза `#C1658A`, оранж `#FFA96C`, розовый `#FEA0EC` и близкие).
  Нужен собственный SkinSpec — как и для всех классов.
- **Корона + зелёная палитра LinkedIn**, их формат Daily #N и шеринг-карточка
  результата.
- **Экран победы референса** как композиция (герой-персонаж по центру +
  конфетти + одна зелёная капсула) — повторять покадрово не надо; праздник
  делаем свой.

### 6.3 Оценка риска

**Низкий, но не нулевой** — совпадает с оценкой shortlist. Риск не в правиле,
а в оформлении: жанр за последние месяцы оброс узнаваемыми визуальными
конвенциями (питомец на клетке, пастельные регионы), и «просто перекрасить»
недостаточно. Требование: собственная тема, уводящая и от кошек, и от корон.

## 7. Что осталось нерешённым (для full pack)

Закрытый список. Всё это — блокеры не для решения «брать/не брать», а для
числового ТЗ.

**Требует device capture (`REFERENCE-DEVICE-LAB`, leash-Android):**

1. **Всё, что измерено выше, снято с неофициального фан-веб-билда.** На
   устройстве нужно подтвердить/опровергнуть: диапазон `N`, пилу размеров,
   двухосевую сложность, givens на первых уровнях, correctness-счётчик,
   marking-модель, отсутствие таймера.
2. **Сердца:** есть ли 3 сердца, что именно их тратит (неверная постановка? X?
   конфликт?), стоимость и время восполнения, rewarded-восполнение.
3. **Лимит подсказок** в оригинале и его монетизация.
4. **Реальная кривая времени человека** по уровням (публичных чисел нет,
   leaderboard фан-сайта засеян). Нужны 8–10 замеров по тирам.
5. **Реклама и её точки** (interstitial между уровнями? rewarded за хинт?) —
   в вебе их нет по определению.
6. **Онбординг первых 10–15 секунд на устройстве**: есть ли интерактивный
   туториал с указующей рукой, или только чипы правил, как в вебе.

**Требует дополнительного анализа (можно без устройства):**

7. **Правило понижения тира**: я играл чисто и видел только `r1 → r2`. Что
   делает `consecutiveFails` / `consecutiveRetryLevels` / `retryTrackingStrategy`.
8. **Точное правило отбора клеток в хинт-батче** (наблюдал 8 клеток при более
   широком реальном замыкании; cap = 8 — гипотеза).
9. **Природа «жёсткого» банка** (уровень 10: без seed, `idx44`, `minRegion 3`,
   требует ветвления; рядом пустой `lkModProgress`). Если верхние тиры
   действительно импортированы, наш генератор обязан уметь то, чего их
   генератор не умеет — иначе получим ту же стену.
10. **Верхняя граница `N`**: `8×8` заявлена как Daily у `queensgames.org`, но
    в наигранной прогрессии максимум — `7×7`. Уточнить, где реально
    останавливается мобильная линия.
11. **Порог «нечестного» уровня**: сколько ветвлений допустимо, прежде чем
    уровень становится угадайкой. Нужен собственный калибровочный прогон
    дедукт-солвера, это условие приёмки нашей фабрики.
12. **LinkedIn Queens first-hand не проверен** (consent/login-стена, не
    логинился). Если нужен именно её feel — это отдельный операторский акт по
    доступу, а не задача researcher'а.
