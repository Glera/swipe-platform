## 3. Цели оператора → главный путь

Все четыре цели (телефон · Telegram · без ожиданий · человеческие статусы)
сводятся к одному пути: **Telegram → открыть нужный объект → сразу понять
статус → проверить → принять решение → следующий объект.** Слайсы ниже
выстроены вдоль этого пути, а не вдоль внутренних подсистем Lab.

Что уже есть: Fast Lane-петля с телефона (пометить → следить → сыграть
кандидата → принять одним Telegram-действием), четыре сигнала, deep-link
`startapp=pr_{releaseId}` в READY-сообщении.
Чего не хватает: принятый end-to-end source для отсмотр-очереди с телефона
(Generator bridge есть, backend/Feed/Telegram delivery не смержены), единый словарь
статусов между Telegram/Lab/лентой (сейчас два wire-формата проекции задач и
реальный finding #98 «странный warning после успешной rework»), замеры
пользовательских интервалов вокруг существующего prefetch,
«почему недоступно» у блокировок, дайджест готовых проверок.

## 4. Слайсы (порядок оператора 13.08; каждый — отдельный bounded PR)

Старт всей очереди — после Labs gate (S9, STATE.md). Оценки — активная
работа; календарно зависит от интерливинга с L1–L4.

**Слайс 1 · Телефонный inbox — `0.5–1 день`.**
Сначала source acceptance на свежих default branches: заменить или
пересобрать старые R7 draft-пакеты Backend/Feed/Generator/Agents, закрыть их
NO-GO и доказать cross-repo contract. Только затем smoke моста mobile-review →
включить `SWIPE_MOBILE_REVIEW_ENABLED`
(операторское действие на живом Lab) → exact deep link из каждого
уведомления в конкретный объект → пройти путь на телефоне целиком.
Экран открывается сразу на нужном кандидате; видны причина и единственное
следующее действие; после решения — переход к следующему; технические
ID/CAS — под «Подробнее». Экран кандидата — **пошаговый**: Играть →
результат прохождения → Принять / Ещё доработать; до прохождения решение
заблокировано с объяснением («Доступно после прохождения») — защита от
случайной публикации. Это UX-порядок экрана, не новая authority: сервер
по-прежнему принимает только content-bound Telegram Approve. v0 = deep
links в существующие экраны моста
(bundle уже компактный, это не адаптация desktop-Lab); отдельный
inbox-список — v1 после наигрыша. Сюда же consumer
`/v1/mobile-reviews/notifications` (P3 от 06.08).
*Оговорка по честности оценки:* Generator bridge влит 06.08, но upstream
source не принят и контур ни разу не соакался. Оценка `0.5–1 день` относится
к UX/smoke после source acceptance; восстановление cross-repo source —
отдельный prerequisite с оценкой владельцев соответствующих repos.

**Слайс 2 · Честные уведомления и статусы — `1–2 дня`.**
Один набор состояний на всех поверхностях (Telegram, Lab, лента):
**В очереди · В работе · Можно проверить · Нужна помощь · Ждёт
подтверждения · Опубликовано.** Для каждой блокировки — «почему» и «что
произойдёт дальше».
**Lineage-правило:** основной статус — текущее эффективное состояние
объекта по голове successor-цепочки (`successorCycle`/`parentReleaseId`
уже есть в данных релизов): если у остановленной попытки есть успешный
successor, наверх поднимается «Опубликовано», а прежний `NEEDS_HELP`
уходит в свёрнутую историю («Предыдущая попытка остановилась»). Mapper
без lineage воспроизвёл бы finding #98 теми же шестью ярлыками.
**Контракт Telegram-сообщения:** статус + причина + ровно один следующий
шаг — либо действие («Открыть подробности», «Сыграть кандидата»), либо
честное «Ничего делать не нужно — система ждёт диагностики».
Закрывает класс «в ленте всё хорошо, а рядом
"автоматическая доработка остановилась"» (зафиксированный UX-finding #98) и
сырой `catch` в `submitReview`. У каждого disabled-действия — человеческое
объяснение (паттерн «выключено → скажи почему» уже есть, тиражировать).
*Инженерная рамка:* это слой представления — один общий словарь-модуль
поверх существующих wire-статусов (`accepted/blocked`,
`preparing/needs_help`, машина релизов). Wire/schemas не трогаем: их смена
тянет rolling-order pin (Backend → Feed → Generator) и cross-Mac церемонию,
что сорвёт оценку 1–2 дня. Маппинг «6 человеческих ← все машинные» — первый
коммит слайса, по нему сверяются все три поверхности.

**Слайс 3 · Скорость отсмотра — `1–2 дня`.**
Проверка уже существующего prefetch следующего кандидата (тёплый фрейм),
сброс пагинации каталога,
boot-waterfall. Метрики — пользовательские, не абстрактная латентность API:
Telegram → кандидат интерактивен; решение → следующий кандидат готов; доля
ожиданий >2–3 с без видимого прогресса (для них — существующий
`beginBusy/progressMarkup`). Замер — простые клиентские метки, расширить
`lab:performance` этими путями.
*Инженерная рамка:* prefetch обязан переиспользовать lifecycle-гарды волн
1–4 — перезапуск живого превью раньше съедал completion-evidence, эта гонка
закрыта и не должна вернуться тёплым фреймом; родственная гонка
level-play-frame числится в follow-ups.

**Слайс 4 · Три комнаты — `0.5–1 день`.**
Этап 1 по готовому ТЗ (+аддендум: 14 view). Имена комнат — человеческие
глаголы: **Проверить · Создать · Опубликовать** (вместо
Отсмотр/Конвейер/Прод). Нюанс третьей комнаты: там же живут отзыв и надзор,
но это по-прежнему комната публикационной власти — имя выдерживает.
**DONE 15.08:** PR #43 / issue #124; legacy `?view`, новый `?room`, per-room
last view, счётчики и guarded `1/2/3` проверены desktop/mobile и CI. Следующие
слайсы сохраняют исходный phone-first порядок.

**Слайс 5 · после телефонного наигрыша — три отдельных bounded PR,
суммарно `2–4 дня`.**
- **5а · Единая очередь + переезд Fast Lane.** Один поток очереди отсмотра
  (тип кандидата — ярлык); панель Fast Lane из «Композера» в «Создать».
- **5б · «Состояние системы».** Вторичный сводный экран: допуски,
  диагностика «Lab включён, а роут/флаг выключен», журнал отправленных
  Telegram-сигналов. Контекстные строки «почему недоступно» у самих кнопок
  появляются раньше — в слайсе 2.
- **5в · Точечные слияния дублей** — каждое отдельным маленьким PR и только
  по доказанной наигрышем боли: recall two-state, три входа rework, два UI
  setting-output. Слияние state-моделей несёт риск регрессий больше
  UI-эффекта — без доказанной боли не трогаем.

## 5. Критерии готовности (принимаются не по наличию экранов)

1. С телефона можно завершить типичный цикл без компьютера.
2. Каждое уведомление отвечает на «что готово?» и «что мне сделать?».
3. Ожидание дольше 2–3 секунд всегда показывает понятный прогресс;
   следующий кандидат предварительно загружен.
4. У каждого disabled-действия есть человеческое объяснение; Telegram, Lab
   и лента показывают один и тот же статус.

## 7. Связь с очередью портфеля (STATE.md 13.08)

Phase 0 идёт параллельно текущему portfolio: сверка master, v2.3 delta,
карта путей и bounded ticket drafts. Авторинг кода допускается только после
path-disjoint admission относительно активных #114/#121; shared
scripts/config/tests или общий release/Lab модуль означают сериализацию.
После отдельно допущенного и уже закрытого слайса 4 сохраняется принятый
оператором порядок остатка:
**слайсы 1–2 → L1 → слайс 3 → L2/L3,
слайсы 5а/5б/5в — только после телефонного наигрыша.** Слайсы 1–2 маленькие
и делают телефонные решения внутри L1–L3 лучше; двигать их дальше — терять
смысл phone-first. Arrows-вариации #92 остаются только в Labs и сами по себе
не являются планом добавления в платформенную ленту.
