# Dev-loop: как пользоваться (гид на пальцах)

Все команды — из корня workspace, если не сказано иное.

## 1. Meta-repo (корень workspace — теперь git)

**Что это.** Корень стал маленьким git-репо, которое хранит только
инструменты и документы (`scripts/`, `docs/`, `VISION.md`, `AGENTS.md`,
`CLAUDE.md`, `.claude/skills/`). Все 22 вложенных репозитория и их
worktree-копии игнорируются.

**Как пользоваться.** Почти никак — оно работает само. Два случая:
- появился новый скрипт/документ уровня workspace → `git add <файл> && git commit`;
- `git status` в корне показывает untracked-файлы (отчёты, html) — это
  напоминание разобрать их по местам, а не мусор.

**Кейс.** Раньше `worktree-status.mjs` жил бы просто файлом на диске и
потерялся бы при переезде. Теперь у tooling есть история и его видят агенты.

## 2. `worktree-status` — порядок в копиях репозиториев

**Что это.** Read-only обзор всех git worktree шести репо.

**Как пользоваться.**
```
node scripts/worktree-status.mjs
```
Таблица: repo / branch / clean-dirty / merged / ahead-behind / дата / путь.
В конце — блок «Safe to remove»: готовые команды `git worktree remove`
ТОЛЬКО для копий, которые clean И влиты в origin/master И не main/locked.
Скрипт никогда ничего не удаляет сам — копируешь команду руками, если согласен.

**Кейс.** Первый же прогон нашёл 7 копий, которые можно снести (6 у
backend, 1 у feed) — это диск и, главное, голова: не надо помнить, «а что
там в swipe-backend-catalog-read». Запускай раз в неделю или после
вливания веток.

## 3. Auto-review skill — независимое ревью до commit/PR

**Что это.** «Свежий взгляд» на твой патч до того, как он попадёт в репо.
Ревьюер-агент слеп к рассуждениям автора (не заражается его логикой), но
видит всю кодовую базу в изолированной копии.

**Как пользоваться.** В Claude Code сессии, где ты (или агент) сделал
изменение, скажи: **«прогони auto-review»** (skill `auto-review`).
Дальше цикл сам:
1. `scripts/auto-review-collect.mjs <репо>` собирает патч (commits от
   base + staged + unstaged + untracked), выкидывает секреты (fail-closed),
   строит изолированный checkout;
2. ревьюер смотрит diff + код и возвращает findings `F001…` с P1/P2/P3;
3. автор обязан по КАЖДОМУ: исправить или отклонить с причиной —
   молча пропустить нельзя (валидатор не даст);
4. повторяются verify-команды репо, резюме идёт в PR description.

**Кейс.** Ты просишь агента добавить endpoint в swipe-backend. Перед
коммитом он сам вызывает auto-review; ревьюер находит «P1: нет проверки
идемпотентности в replay-ветке» — автор чинит в своей сессии, где у него
контекст, и в PR попадает резюме «нашли 3, исправили 2, отклонили 1
(осознанный дизайн, причина …)». Ты читаешь полстраницы вместо диффа.
**Пилот: следующие 10–20 реальных изменений backend/generator.**

## 4. Visual-proof — ролики «было/стало» для playables

**Что это.** Автоматическая запись автоплея уровня в двух изолированных
сборках: base (before) и base+твой патч (after). Реальный темп, честная
победа (WIN только от события механики), fail-closed.

**Как пользоваться.** Из `playables/`:
```
npm run visual-proof pins-ftue -- --level 6 --include pins-ftue/src/levels.ts
```
- `--include <пути>` — какие изменения доказываем (иначе весь патч);
- `--runs 2` — по два прогона для проверки стабильности;
- `--both <пути>` — правки, применяемые к ОБОИМ сборкам (например,
  ещё не закоммиченный debug-hook).

Результат: `.artifacts/visual-proof/pins-ftue/<время>/…` — `run.webm` +
кадры mount/mid/win + `result.json` (что применяли, sha, исходы) +
сами байты патча (`applied.patch`). Смотришь два ролика — принимаешь решение.
Провал (lose/timeout/ошибка/не смонтировалось) = ненулевой exit, красиво
упасть «с видео» нельзя.

Debug-hook: `?autoPull=p57388,p99142,…` в URL swipe-сборки задаёт порядок
автоплея pins — работает в любом уровне, без параметра прод не тронут.

**Кейс.** Правишь геометрию L6 в pins-ftue. Вместо «собрать, открыть,
доиграть, повторить для соседних» — одна команда, 60 секунд, и у тебя
пара роликов: на after булавка сдвинута, на before нет, соседний уровень
не задет. Это же — артефакт для PR: ревьюер видит доказательство глазами.

## 5. CI пяти репозиториев — «у меня работает» больше не аргумент

**Что это.** Каждый push/PR в swipe-agents, swipe-ugc, swipe-generator,
feed-prototype прогоняет их verify на чистой машине GitHub (+ у playables —
path-scoped тесты visual-proof; у backend — полный PostgreSQL acceptance,
он был и раньше).

**Как пользоваться.** Никак — просто пушь. Смотреть: `gh run list --repo
Glera/<репо>` или вкладка Actions. Красный = чинить до merge.

**Кейс из жизни (сегодняшний).** Generator был «зелёный локально», а CI
вскрыл две скрытые зависимости от твоей настроенной машины: Node-версию и
то, что `level-gate --identity` требует установленный сосед swipe-ugc.
Оба класса «сломается только в проде» теперь ловятся до merge.

**Reverse-drift гейт.** Если изменишь контрактную фикстуру в
`swipe-backend/docs/specs/fixtures/` — backend-CI станет красным с
сообщением «обнови вендоренную копию в generator/feed» (читает их
настоящие копии: feed — публичный checkout, generator — по read-only
deploy key). Забыть downstream больше невозможно.

## 6. VISION.md + AGENTS.md + docs-boundary lint — навигация для агентов

**Что это.**
- `VISION.md` — одна страница «куда движется продукт и чего не делаем»;
- `AGENTS.md` — карта: репо → назначение → главные доки → verify-команда →
  границы;
- `scripts/docs-boundary-lint.mjs` — следит, чтобы в CLAUDE.md не заводились
  протухающие утверждения («сейчас зелёное», «текущий head»).

**Как пользоваться.**
- Твоё разовое действие: дочитать VISION.md и снять плашку «ЧЕРНОВИК».
- Агентам: «сверь идею с VISION.md», «возьми verify-команду из AGENTS.md».
- Lint: `node scripts/docs-boundary-lint.mjs` — сейчас advisory (3 known
  нарушения до doc-split), после разделения документации станет гейтом.

**Кейс.** Приходит идея «давай добавим кнопку "ещё такого"». Агент сам
отвечает: «противоречит VISION §НЕ делаем (спрос выводится из поведения)» —
твоё внимание вообще не потрачено. Или новый субагент начинает работу с
generator — он не спрашивает тебя, как проверять: `npm run verify` написан
в таблице.

## Куда это складывается

Правило одно: **изменение не считается готовым, пока у него нет
доказательств, которые можно посмотреть за минуту** — резюме auto-review,
пара роликов visual-proof, зелёный чистый CI. Твоя роль смещается с
«проверить всё» на «решить по доказательствам».
