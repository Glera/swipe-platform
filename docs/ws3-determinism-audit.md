# WS3.0 — Аудит детерминизма пилотной механики (pins / pins-ftue)

Read-only аудит для visual-proof skill (dev-loop.md, WS3). Ничего в репозиториях
не менялось. Дата: 2026-07-17.

Пилот: `playables/pins-ftue` — это **отдельная директория механики внутри
единого git-репо `playables`** (не отдельный репозиторий). `pins`, `pins-ftue`,
`pins-v1`, `pins-swipe`, `pins-v1-swipe` — форки одного движка в том же репо.
Логика идентична (`src/main.ts`, `src/physics.ts`, `src/levels.ts`,
`src/finger-prerendered.ts`); pins-ftue дополнительно несёт

## 1. Источники недетерминизма

### 1a. `Math.random()` — есть, не сидируется нигде

Единого PRNG в репозитории **нет** (grep по `mulberry/xorshift/sfc32/seedrandom/
createRng` — пусто). Везде голый `Math.random()`. Две категории:

**Влияет на геймплей/траекторию (критично):**

- `pins/src/main.ts:492` (и `pins-ftue/src/main.ts:599`) — `autoNextPin()`:
  ```
  return pool[Math.floor(Math.random() * pool.length)];
  ```
  **Это доминирующий источник расхождения.** `autoNextPin()` следует
  авторскому порядку `level.autoPull`, НО **ни один уровень не задаёт
  `autoPull`** (grep `autoPull:` в обоих `levels.ts` = 0 совпадений; есть только
  объявление типа). Значит autoplay ВСЕГДА падает в random-ветку и тянет пины в
  случайном порядке при каждом прогоне → разный каскад монет → разный финальный
  пайл. Без фикса два прогона одного уровня расходятся уже на порядке действий.

**Влияет только на визуал/аудио (допустимо для «глаз», ломает пиксель-diff):**

- `physics.ts:316,497` — `Matter.Body.setAngle(body, Math.random()*2π)` при
  спавне монет/камней. Тела круглые → на физику НЕ влияет, но вращает спрайт
  монеты (визуальный поворот стартовой раскладки).
- `physics.ts:507-520` — тайминги/фаза «блеска» монет (`shineShowMs`,
  `shineOffsetMs`, `spinningStep`); `physics.ts:539` — вспышка при столкновении.
- `main.ts:338-361` — снег (позиции/скорость/дрейф/фаза каждой снежинки);
  `main.ts:4197-4242` — пузыри воды и поток в трубе; `main.ts:492` (pool pick);
  `main.ts:1319` — выбор coinGlass sfx; `main.ts:1352-1356` — выбор и расписание
  «cold voice» реплик; `pins-ftue/src/main.ts:3860` — выбор туториал-пина.

Замечу: стартовая **раскладка** монет (позиции) уже детерминирована —
`fillSpawnBand`/`prePlaceCluster` используют `seededSigned(index)`
(`physics.ts:362`, `sin(seed*12.9898)*43758.5453` — index-based, стабильно между
рестартами). Random там только на угол (визуал). То есть половина работы по
seed-стабильности спавна уже сделана — не хватает только PRNG для порядка
autoplay и для угла.

### 1b. Date.now / performance.now в геймплей-логике

- `Date.now()` — только в `editor.ts` для генерации id новых объектов (не в
  рантайме плеера). Геймплея не касается.
- `performance.now()` — **везде** как игровые часы: `levelStartMs`,
  `lastFrameMs`, autoplay-расписание (`autoLastPullMs`, `autoLastInteractionMs`),
  тайминги пинов/сосуда, breathing-фаза руки (`AutoCursor.gesture` →
  `Math.sin(now/430)`). Это и есть корень проблемы связки «реальное время ↔
  фикс-шаг» (см. 1c).

### 1c. Физика: фикс-шаг, но связка с rAF по стенным часам (ГЛАВНАЯ проблема)

Физика **сама по себе детерминирована**: фикс-шаг аккумулятор
(`stepPhysics`, `physics.ts:777`), шаг `1000/60` (light) или `1000/120`
(strict), `Matter.Engine.update(engine, fixedDtMs)`, анти-туннелинг velocity-
clamp ПЕРЕД интеграцией, catch-up ≤ `maxSubsteps`, остаток аккумулятора
сбрасывается при упоре в кап. Matter.js при идентичной последовательности шагов
и идентичных входах воспроизводим.

**Но** главный цикл (`main.ts:2402 loop()`) считает
`dt = min(now - lastFrameMs, 1000/15)`, `now = performance.now()`, и кормит этим
аккумулятор. Число физ-шагов за кадр = сколько реального времени налилось. При
этом **autoplay-действия срабатывают по расписанию performance.now**
(`AutoCursor.update` fires `onAction` при `el >= actionAt`; `updateAutoPlay(now)`
с `now = performance.now`). Итог: **момент релиза пина относительно
накопленного sim-времени зависит от реального пейсинга кадров.** Даже с
одинаковым seed дрожание FPS сдвигает, на каком именно sim-шаге релизится пин →
хаотическое расхождение пайла монет (система чувствительна к начальным условиям).
Это то, что фикс-шаг сам по себе НЕ лечит — нужна детерминированная связка часов
(см. §5).

`physMode` (strict 120Гц / light 60Гц) — **не device-dependent**: это
фиксированный дефолт на механику (pins → strict, pins-ftue → light), меняется
только через `?phys=` (`main.ts:671`, `pins-ftue/main.ts:791`). То есть таймстеп
воспроизводим, GPU/девайс на выбор профиля не влияют. Хорошо.

### 1d. Анимационные тайминги

Все на `performance.now`: fade сосуда (`VESSEL_FADE_MS`), win-видео, glow-цикл
пинов (`PIN_GLOW_CYCLE_MS`), breathing руки, snowStep(dt). Детерминированы при
детерминированных часах; иначе — плывут с реальным временем.

### 1e. Загрузка ассетов / race

Видео-слои (`bgVideoBase/Win/Post`, персонажи `dog_st/alex_st/emma_st`,
Stage_1/2/3) — inline base64 в бандл (`?inline`), сетевого race нет. Но
**видео декодируется в реальном времени**: `warmup()` ждёт первый PAINTED кадр
через `requestVideoFrameCallback`, дальше `currentTime` идёт по стенным часам.
Кадр видео в момент скриншота/записи зависит от таймингов декода → неизбежный
допуск (см. §6). Изображения (finger, sprites) — тоже inline, `img.complete`
проверяется. Реального сетевого гонки нет.

### 1f. Spine

Рантайм-Spine в pins/pins-ftue **нет**. Персонажи — видео (mp4/webm), рука —
запечённый PNG (`finger-prerendered.ts`). Скелетной Spine-анимации в рантайме
плеера, которая давала бы недетерминизм, здесь не задействовано (Spine-prerender
из CLAUDE.md относится к другим механикам). WebGL есть только в
`pins-ftue/water-gl.ts` (метаболы воды) — это чисто рендер, GPU-зависимый (§6).

## 2. AutoCursor-сценарий

`shared/auto-cursor.ts` — **полностью детерминированная чистая функция** от
(`now`, последовательность действий). Константная скорость:
`travelMs = clamp(hypot(dx,dy)/refLen * MS_PER_CELL, MIN, MAX)`; фиксированные
сегменты tap/drag; breathing = `Math.sin(now/430)`. Никакого random внутри.
Позиция/жест воспроизводимы при воспроизводимом `now` и той же цепочке actions.

**Но выбор цели — НЕ в AutoCursor, а в механике** (`autoNextPin`, §1a). Модуль
явно это документирует: «What stays per-mechanic (NOT here): which move to make».
В pins цель выбирается: сперва `level.autoPull` (нигде не задан) → иначе
`Math.random()` по пулу idle-пинов. Значит **траектория руки детерминирована,
а ПОРЯДОК/ЦЕЛИ — случайны**. Плюс момент запуска следующего действия зависит от
`coinsAreSettledEnough(now)` (скорости монет) и от гейтов
`AUTO_MIN_GAP_MS=600`/`AUTO_MAX_GAP_MS=3200` — т.е. от физ-состояния и часов.

Autoplay запускается хостом: `window.__playable.swipe.startAutoPlay()`
(`registerSwipeApi`, `main.ts:2470`). Отдельного `?autoplay=1` param нет —
харнес должен дёрнуть API.

## 3. Seed / level / query-инъекция: что есть, чего нет

Существующие query-параметры (grep `URLSearchParams`/`location.search`):

| param | где | назначение |
|---|---|---|
| `?level=N` | `main.ts:637`, `pins-ftue:744` | **выбор уровня — ЕСТЬ** (`parseInt`) |
| `?phys=strict\|light` | `main.ts:671` | профиль физики (таймстеп) |
| `?perf=1` | `main.ts:1493`, quality.ts | perf-HUD / телеметрия |
| `?quality`,`?tier`,`?dpr` | quality.ts | тир качества + DPR override |
| `?series`,`?lang`,`?debug`,`?hud`,`?hostPaused`,`?warmpaint`,`?noexpand` | shared | прочее |

**`?seed=` НЕ существует.** PRNG-модуля нет. Уровень фиксируется (`?level=`),
качество/DPR/физпрофиль фиксируются — а вот случайность autoplay и ambient не
сидируется ничем.

### Минимальный диф для seed-инъекции

Оценка: **малый, ~4 файла, ~25 строк продуктового кода** (для пилота):

1. **`shared/rng.ts`** — новый файл, seeded PRNG (mulberry32 + строковый seed→
   uint32). ~15 строк. Экспорт: `makeRng(seed)`, singleton `rng()` +
   `initRng(seedFromQuery)`.
2. **`pins/src/main.ts` и `pins-ftue/src/main.ts`** — распарсить `?seed=` рядом
   с `?level=` и вызвать `initRng(seed)` до `startLevel`. ~4 строки ×2.
3. **Роутинг критичного random через seeded PRNG:** `autoNextPin()` random-pick
   (`main.ts:492` / `pins-ftue:599`) → `rng()`. ~1 строка ×2. **Либо** (data-only,
   без кода) **задать `autoPull: [...]` для пилотных уровней** в `levels.ts` —
   это фиксирует порядок и снимает доминирующее расхождение вообще без PRNG.
4. **Для визуальной стабильности** (опционально, если хочется ближе к
   пиксельному сходству): `setAngle` монет (`physics.ts:316/497`) →
   `seededSigned(i)`; ambient-random (снег/пузыри/блеск/voice) → `rng()`.
   Ещё ~6-8 точек ×2 файла. Для «сравнения глазами» этот шаг НЕ обязателен.

Достаточный минимум для воспроизводимого прогона пилота = пункты 1–3 (или даже
только 3 через `autoPull` для конкретного уровня). Пункт 4 — косметика под более
строгое сходство.

## 4. Playwright-харнес release-гейта

Живёт в `playables/scripts/checks/`:

- **`runtime.mjs`** (939 строк) — те самые «20 проверок» + скриншоты.
  `chromium.launch()` (headless), поднимает **свой http-сервер на свободном
  порту** (`serveDist` + `getFreePort`), отдаёт `dist/index.html` (single-file
  прод-бандл). Контекст: `browser.newContext({ viewport:{390×844},
  deviceScaleFactor:2, hasTouch, isMobile })`. Скриншоты — `page.screenshot`
  на 4 пресетах × 2 ориентации в `test-results/<id>/`. Дополнительно гоняет
  iOS/iPad/WebKit-подобные контексты и CPU-throttle через CDP.
- **`ftue-playtest.mjs`** (113 строк) — ближайший к «проиграть уровень»
  харнес, НО: грузит per-level экспорт `playables-export/<id>-lN.html` через
  `file://`, viewport `412×915`, инжектит `PlayableHost`-stub + rAF-FPS-метр,
  CPU-throttle CDP, и **драйвит НЕ через autoplay, а грубым тапом 3×3 сетки**
  (`page.touchscreen.tap` по `[0.25,0.5,0.75]×[0.34,0.5,0.66]`) c
  `waitForTimeout`. Для visual-proof не годится как есть (не AutoCursor, тайминги
  через wall-clock waitForTimeout).

**Навесить запись видео — тривиально.** Playwright `recordVideo` задаётся в
`newContext({ recordVideo:{ dir, size } })`, а харнес уже создаёт контексты с
известным viewport и уже поднимает изолированный прод-билд на localhost. То есть
инфраструктура (изолированный сервер + фикс-viewport + скриншоты) готова; для
WS3 нужно: (a) собирать/отдавать **swipe/full-таргет** (с autoplay-API), а не
single-file AppLovin-бандл; (b) после `ready` дёрнуть
`window.__playable.swipe.startAutoPlay()`; (c) добавить `recordVideo` в контекст.

Viewport по умолчанию: `390×844 @2x` (runtime.mjs) либо `412×915 @DPR`
(ftue-playtest) — оба фиксируемы, для WS3 надо выбрать один канонический.

## 5. Вердикт

### (a) Что УЖЕ детерминировано

- Движок физики — фикс-шаг аккумулятор + Matter.update(fixedDt), анти-туннелинг,
  bounded catch-up. Воспроизводим при идентичной последовательности шагов/входов.
- Стартовая **раскладка** монет (позиции) — `seededSigned(index)`, стабильна.
- `physMode`/таймстеп — фикс-дефолт на механику, не device-dependent, `?phys=`.
- AutoCursor (движение руки + жест) — чистая функция от `now`+actions, без random.
- Выбор уровня (`?level=`), тир/DPR/качество (`?tier/?dpr/?quality`) —
  параметризуемы и фиксируемы.
- Ассеты inline (нет сетевого race).
- Playwright-харнес уже: изолированный прод-билд на localhost, фикс-viewport,
  скриншоты; `recordVideo` добавляется одной опцией контекста.

### (b) Минимальные правки для воспроизводимого прогона уровня N в реальном темпе

1. **Порядок autoplay** (обязательно): задать `autoPull: [...]` для пилотного
   уровня в `levels.ts` (data-only, ~1 строка), ИЛИ ввести seeded PRNG и
   прогнать `autoNextPin` через него. Без этого порядок пинов случаен → прогоны
   несопоставимы. Это доминирующий фикс.
2. **`shared/rng.ts` + `?seed=`** (~15 + 4×2 строк): singleton seeded PRNG,
   инициализируемый из query, до `startLevel`.
3. **Детерминированная связка часов в ХАРНЕСЕ** (не продуктовый код, ~40 строк
   в новом visual-proof скрипте): через `page.addInitScript` подменить
   `performance.now`/`Date.now` виртуальными часами и `requestAnimationFrame` —
   шимом, продвигающим часы на фикс-dt каждый кадр. Тогда autoplay-расписание и
   физ-аккумулятор идут в локстепе → траектории монет воспроизводятся, а не
   «примерно похожи». Это апгрейд от «сопоставимо» к «воспроизводимо» без правки
   игры. «Реальный темп» сохраняется, если dt=16.67мс и кадры гонятся с реальной
   частотой; при желании можно рендерить оффлайн-быстрее, а видео писать по
   виртуальному времени.
4. **Харнес WS3** (новый скрипт поверх существующего): собрать swipe-таргет,
   отдать на localhost, `newContext({recordVideo})` с каноническим viewport,
   `goto('...?level=N&seed=S')`, дождаться `ready`, дёрнуть `startAutoPlay()`,
   писать WebM + ключевые PNG (mount/mid/win), скопировать в
   `<workspace>/.artifacts/visual-proof/...`.
5. (Опц., под более строгое сходство) заменить визуальные `Math.random` (угол
   монет, снег, пузыри, блеск, voice) на seeded PRNG.

### (c) Неизбежные допуски → почему «глазами по двум роликам», а не пиксель-diff

- **Видео-слои** (фон Stage_1/2/3, персонажи, win-видео): `currentTime` идёт по
  стенным часам и GPU-декоду; точный кадр в момент записи плывёт ± несколько
  кадров, даже при вирт-часах (video-decode вне нашего клока).
- **WebGL-вода pins-ftue L7/L8**: метаболы на GPU; растеризация/precision
  различаются между GPU/драйвером/SwiftShader (headless) → пиксельно нестабильны
  by design.
- **Canvas antialiasing + DPR-округление**: субпиксельные различия рендера между
  прогонами/машинами.
- **Длительность ролика ±**: готовность видео (`requestVideoFrameCallback`) и
  реальный пейсинг дают разброс в несколько кадров; спека уже допускает
  «длительность в допуске».

Поэтому корректный критерий сравнения before/after — **человеческий глаз по двум
коротким роликам** (тот же уровень, тот же порядок пинов, тот же финальный
win-стейт, сопоставимая длительность), а не пиксельный diff, который завалится на
видео/WebGL/AA-шуме, ничего не говоря о смысле правки.

## Готовность к WS3: **YELLOW**

Не RED: архитектура детерминизму не противоречит — фикс-шаг физика, seeded
раскладка спавна, общий константный AutoCursor, параметризация level/tier/DPR,
готовый изолированный Playwright-харнес с localhost-сервером и скриншотами;
`recordVideo` — одна опция.

Не GREEN: **пути seed нет вообще** (`?seed=`/PRNG отсутствуют), и **порядок
autoplay сейчас `Math.random` без авторского `autoPull`** — два прогона одного
уровня расходятся уже на порядке действий. Плюс связка «реальное время ↔
фикс-шаг» требует детерминированного клока в харнесе, иначе даже при seed
траектории монет плывут.

Разблокировка дешёвая и хорошо ограниченная: (1) `autoPull` для пилотного
уровня ИЛИ seeded PRNG на `autoNextPin`; (2) `shared/rng.ts` + `?seed=`;
(3) вирт-часы+rAF-шим в скрипте visual-proof. Продуктовый диф ~25 строк в
~4 файлах; остальное — код самого харнеса. После этого пилот `pins-ftue`
воспроизводим в рамках допусков §5(c).
