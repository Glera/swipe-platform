## #15 — P1: самоаттестация внутри процесса не доказывает, что исполняется

`p4g-agent-phase-b0-release-candidate.mjs`

Оба новых гейта — `git status --porcelain=v1 --untracked-files=no`
(`:143-158`) и побайтовое сравнение закрытия модулей с блобами `sourceCommit`
(`:159-169`) — вызываются из `assertExactSource` на `:554`, то есть **внутри
`buildReleaseCandidate` (`:550`)**, после того как все импорты (`:3-21`) и
top-level код самого модуля уже исполнены.

Следствие: отравленный билдер, восстанавливающий свои коммитные байты на
импорте (`git checkout --` по себе), проходит оба гейта детерминированно.
Worktree после прогона чист, `git status` пуст, байты на диске равны
коммитным — а исполняется отравленный код, уже загруженный в память. Двойная
сборка из того же чекаута снова **подтверждает** тампер. Программа не может
засвидетельствовать собственную целостность; проверка доказывает лишь
состояние диска в момент проверки.

Второй вектор, не трогающий отслеживаемые байты вообще: **у билдера нет
враппера.** Рунбук (`:358`, `:361`) запускает его как
`/usr/local/bin/node host/phase-b0/p4g-agent-phase-b0-release-candidate.mjs …`
прямо из операторского шелла, тогда как каждая другая привилегированная точка
входа идёт через `exec /usr/bin/env -i $CLEAN_ENV` (например
`p4g-agent-phase-b0-prepare:34`). Защиты от `NODE_OPTIONS` в билдере нет ни
одной (грепом — ноль упоминаний). `NODE_OPTIONS="--import ./preload.mjs"` с
untracked-файлом невидим для `--untracked-files=no`.

Наивная атака R2 при этом закрыта честно: прямой патч → `release_candidate_
source_dirty`; спрятанный через `assume-unchanged` → `release_candidate_
builder_identity`.

**Фикс — один структурный, закрывает сразу три находки.** Дать билдеру и
установщику такой же враппер, как у всех: враппер материализует закрытие из
`sourceCommit` во временный каталог (механизм `readGitObject`/
`materializeTree` уже есть) и делает `exec /usr/bin/env -i node` уже по этой
копии. Доверие уезжает из проверяемого процесса; `NODE_OPTIONS`-вектор
умирает вместе с `env -i`.

## #16 — P1: квитанция отката недостижима в штатном пути

`phase-b0-acceptance.mjs:1855-1869`

Новый root-пробник lease исполняет
```sql
SELECT hex(status)||'|'||hex(holder)||'|'||COALESCE(CAST(expiry AS TEXT),'')
  FROM trigger_leases WHERE fingerprint='supervised-runtime' LIMIT 1;
```
и требует от вывода регексп `^([0-9A-F]*)\|([0-9A-F]*)\|(-?\d+)$` — то есть
**непустой expiry**. А штатное освобождение лизы обнуляет и holder, и expiry
(`src/store/projections.ts:204`: `status='released', holder=NULL,
expiry=NULL`).

Воспроизведено мной реальным `/usr/bin/sqlite3` с точным запросом и регекспом
из кода:
```
released → [72656C6561736564||]                                    матчится: false
claimed  → [636C61696D6564|737570657276697365642D72756E74696D653A313233|99999]
                                                                    матчится: true
```

Штатная последовательность отката: `control disable` → `bootout` → SIGTERM →
supervised отпускает лизу (`released/NULL/NULL`) → `control:200` зовёт
`rollback-receipt` → `inspectRollbackLeaseAsRoot` → `root_store_probe_invalid`.
Под `set -euo pipefail` скрипт падает до печати успеха, а
`phase-b0-rollback-receipt.json` не создаётся никогда.

Инверсия делает дефект особенно неприятным: если рантайм **убить** `kill -9`,
строка остаётся `claimed` и квитанция получается; ломается именно **чистое**
завершение. Тест покрывает только `claimed` — ни одного состояния с
`expiry IS NULL`.

**Фикс:** отдавать NULL отличимо (`quote(expiry)` либо
`CASE WHEN expiry IS NULL THEN 'null' …`), трактовать пустой expiry как
«не claimed», и добавить негативы `released`/`expired`/`unclaimed`.

### #16 — P2

1. **Пин restic отключается любым путём ≠ `/usr/local/bin/restic`**
   (`phase-b0-remote-sync.mjs:128-143` — ранний `return` при несовпадении
   пути; тот же short-circuit у гейта owner/mode на `:739-744`). `--restic` —
   свободный абсолютный путь. Все обёртки хардкодят продовый путь, но
   p4g_runner может запустить модуль напрямую и получить непроверенный бинарь.
   Тестовое следствие тяжелее: **все** интеграционные restic-тесты используют
   tmpdir-фикстуру и потому всегда попадают в short-circuit — удаление
   вызова пина из `resticIdentity:754` оставляет набор зелёным (проверено
   мутацией). Это ровно «инертная инъекция».
2. **`startLiveAcceptance` заменил живой внешний якорь времени на
   самоподписанный документ** (`:1650-1712`): раньше он сам дёргал B2-probe и
   `systemsetup`, теперь читает
   `agents.phase-b0-acceptance-start-preflight.v1` из root-owned файла и верит
   ему; единственная привязка к живости — контемпоральность по часам того же
   хоста. То есть `providerObservedAt`, который рунбук описывает как
   независимое наблюдение времени Backblaze, поставляется документом, который
   root может сфабриковать целиком, включая `providerProbeDigest`. Это тот же
   класс, что зафиксированное в проекте «no activation route may accept
   caller-authored JSON».
3. **Ускорение bootstrap повысило вероятность отказа другого типа.** Между
   `launchctl bootstrap` и `captureSystemLaunchdSnapshot` теперь только три
   `launchctl print` и старт node, а `p4g-agent-unattended` до `exec`
   выполняет полноценный `resolve` с обходом и хэшированием всего дерева
   релиза — всё это время дочернего caffeinate не существует, `launchctl
   print` уже отдаёт pid, и `caffeinateMatches.length !== 1` даёт
   `ambiguous_caffeinate_pid` → EXIT-trap → снос всех трёх джоб. Ни retry, ни
   ожидания нет.
4. **Зрелость аудита снята полностью, а не сужена** (`:531-536`): слепота к
   зависшим ранам закрыта, но теперь любой in-flight ран на границе окна даёт
   `started:1` и валит приёмку. Тест фиксирует это как желаемое, рунбук
   перекладывает на оператора («choose an audit end after the final in-flight
   run has become terminal»). Отказ восстановим, поэтому P2, но ранее
   заявленная гарантия «prevents a transient audit failure at the exact
   schedule boundary» заменена ручной дисциплиной.

Отдельно к операторскому утверждению про хостовый restic: на типовой
Homebrew-установке `/usr/local/bin/restic` — симлинк с 0755 и не-root
владельцем, поэтому отказ придёт как `insecure_restic`, **а не**
`unreviewed_restic_binary` — owner/mode проверяются раньше дайджеста.
Fail-closed соблюдён, но проверяется не то, что заявлено.

## Системное наблюдение по трём раундам

Каждый раунд закрывает конкретный экземпляр и оставляет класс:

- R1 → R2: `git archive` заменён обходом графа объектов — но снят гейт
  чистоты, и билдер стал непроверяемым.
- R2 → R3: гейт возвращён — но поставлен внутрь процесса, после загрузки
  проверяемого модуля.
- R2 → R3: `liveRuntimeLease` перестал быть самозаявлением runner'а — но
  новый root-пробник ломает штатный откат.

Причина не в аккуратности исполнителя: правки делаются точечно, в том же
месте, без пересборки границы доверия. Рекомендую перед следующей передачей
**одно структурное изменение вместо трёх точечных**: врапперы `env -i` +
verify-then-exec по материализованной копии для билдера и установщика; для
#16 — NULL-различимый вывод пробника и правило, что каждый новый путь отказа
получает тест **на месте вызова**, а не в изоляции (мутация вызова должна
ронять набор).

Отдельно, вне диффов: набор, который служит receipt'ом, нестабилен в
параллельном прогоне. Мой прогон — 496/498; второй отказ,
`tests/bot/bind.test.ts`, в одиночку проходит 6/6. Причина найдена:
`backup-commit-race`, `data-root-race`, `concurrency` и `supervised`
параллельно запускают `npm run build` в общий `REPO_ROOT`, пока `bind.test.ts`
и `symlink-entrypoints` резолвят симлинки внутрь того же `dist/`. Это
объясняет и флак, который я поймал в R2, и RPC-таймаут из вашей диспозиции.
Практика «параллельный красный — берём серийный» съедает сигнал; чинится
`globalSetup` или отдельным `outDir`.
