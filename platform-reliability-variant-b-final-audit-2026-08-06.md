образом физически недостижимо (`ISLAND_BAKE_READY_FILE` выставлялся только в
`start-bake-runtime.sh`, который был CMD у `Dockerfile.bake`). Манифест кандидата
перескачан из артефакта прогона `31028527617` и пересчитан: `cf2cb0cf…7cc2`,
внутри `image.digest = sha256:d7db2713…b8b4`, `sources.backend.sha = 0e9e940`.

**БД на 0073 — прямым логом деплоя, а не квитанцией.** Лог `dep-d9q1vo7avr4c73akv7k0`:

fail-closed ждёт его до эмиссии квитанции.

**Исполнение по маршруту.** Ровно авторизованные dispatch, все с головой

## P0 — требует действия оператора

1. **Висящее превью `exe-d9pg7s3m8hqs73fguv80` живо, с активной кнопкой
   Approve.** Один клик возвращает сервис с image-рантайма на сборку из
   `./Dockerfile`, то есть отменяет весь манёвр. **Хуже: штатный capture-инструмент
   его не видит** — в квитанциях фаз 2 и 3 стоит `pendingPreviewIds=[]`, то есть
   ложноотрицательный результат защиты, которую мы для этого и строили. Нужен
   durable-вариант (пересоздание/отвязка блюпринта или подтверждённое провайдером
   истечение), а не правило «не нажимать».
2. **SSH-ключ `claude-ops` использовался внутри окна манёвра** (последнее
   использование попадает в интервал 05:20–06:06Z 06.08). Отзыв API-ключа этот
   канал не закрывает, в Events сервиса он не виден. Если это не оператор — инцидент;
   если ключ больше не нужен — отозвать.
3. **Нет резервных кодов 2FA** (на странице стоит «Get Codes», то есть коды не
   выпускались). Один оператор + TOTP без recovery = единая точка отказа для всего
   прода.

  (ветка `claude/mission-truncate-guard`, `55a5656`, в origin отсутствует).

- **В замороженных PR — реальные коллизии нумерации миграций** поверх уже
  применённой в проде цепочки: номера `0070`–`0072` переиспользованы. Требуется
  поимённая диспозиция: часть закрыть как superseded, часть перенумеровать до
  любого merge.
- **Строка `platform_release_receipts` не наблюдалась напрямую** — доказательство
  держится на exit-коде verification job и fail-closed контракте кода. Один
  read-only SELECT закрыл бы это окончательно.

## P2

- **Публичный канал идентичности прода утрачен**: `/api/health` теперь всегда
  `build="dev"`, запечённый в образ `platform-backend-sha` ничем не отдаётся,
  эндпоинта версии/ревизии нет. Каждый следующий вопрос «что крутится в проде»
  требует доступа к дашборду. Стоит отдавать наружу digest + alembic-ревизию.
- **Идентификаторы из дашборда не зафиксированы в квитанциях**: config-digest
  `270e75d…91db1` (самая заметная строка в events) и predeploy digest
  `53657995…6d69` из лога отсутствуют во всех квитанциях — оператору не с чем
  сверять.
- **Документация устарела**: `CLAUDE.md` утверждает `bake_runtime=ready`, а прод
  по замыслу отдаёт `local`; данные ростера в `STATE.md` (13 mappings / прошлая
  активация) уже не актуальны.
- **Прод ≠ master**: образ собран из `0e9e940`, `origin/master` ушёл вперёд
  (дельта — только docs). Формулировка цели «master деплоится» больше не буквальна.
- **Внешний ingress к PostgreSQL, судя по неслитому PR #26 и отсутствию
  `ipAllowList`, остаётся открытым.**

## Оценка работы исполнителя

Манёвр проведён дисциплинированно: границы GO соблюдались, ни одного действия
вне разрешённого объёма, порядок «ревью → merge» восстановлен после единственного
нарушения, каждое замечание ревьюера закрывалось буквально, а не по форме.
Три предыдущих NO-GO (P1 патча B, P1 среза v2, условия v3) были отработаны
содержательно. Единственный системный промах — ложноотрицательный
`pendingPreviewIds=[]`: инструмент, созданный ради обнаружения висящих превью,
их не обнаружил, и это не было замечено до финального аудита.
