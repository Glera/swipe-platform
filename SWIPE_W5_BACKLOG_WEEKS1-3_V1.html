Решения на ревью

D1 · Схема БД v1 — ключевые отличия от SHARE-плана

Три правки к исходной схеме: (1) challenge_attempts вместо одного recipient_id — групповые чаты как главная виральная поверхность; (2) variants — замороженные спеки как решение детерминизма (challenge ссылается на variant_id); (3) events — телеметрия в тот же Postgres.

challenges                       -- было: recipient_id/recipient_value → УДАЛЕНЫ
  id, challenger_id, mechanic_id,
  variant_id uuid NOT NULL REFERENCES variants,   -- замороженный конфиг уровня = честность
  metric_key, challenger_value,
  prepared_message_id, status, created_at, expires_at

challenge_attempts               -- NEW: N участников на вызов
  challenge_id  uuid   REFERENCES challenges
  recipient_id  bigint REFERENCES users
  metric_value  numeric NULL
  beat          boolean NULL                       -- побил ли челленджера
  status        text   'opened'→'completed'
  opened_at, completed_at
  PRIMARY KEY (challenge_id, recipient_id)
  CHECK (recipient_id != challenger-владелец — на уровне API)

variants                         -- NEW: спека = данные (из VARIATION-дока §7)
  id uuid PK, parent_mechanic text, schema_version int,
  params jsonb, skin jsonb, validated jsonb,
  source text ('manual'|'procedural'|'model'), created_at

reward_ledger                    -- reasons ДОПОЛНЕНЫ:
  reason: 'level_win'            -- NEW: базовые звёзды ленты — иначе D1 немерим
        | 'challenge_recipient' | 'challenge_recipient_beat_bonus'
        | 'challenge_challenger' | 'referral_levelup' | 'adjustment'
  idempotency_key:
    level_win  → 'lw:{run_id}'                    -- run_id = client-uuid попытки
    challenge  → 'ch:{challenge_id}:{recipient_id}:{role}'

events                           -- NEW: append-only телеметрия
  id bigserial, user_id bigint NULL, session_id text,
  name text, props jsonb, client_ts timestamptz, created_at
  INDEX (name, created_at), INDEX (session_id)

users, friend_edges, level_results — как в SHARE-плане без изменений. level_results.level → variant_id (унификация нейминга уровней решается сама).

D5 · Клиентские решения

  • Host-джукбокс (звук). AudioContext живёт на хост-странице (разблокируется первым свайпом — жесты ленты идут на хост); юниты шлют {sfx:'win'|'star'|'levelup'} через существующий postMessage-канал Swipe API. Решает немоту пассивной ленты: per-iframe user activation обходится легально. Win-стингер + звук звезды + свайп-свуш, всё ≤ 3 семплов в v1.
  • Хаптика. Telegram.WebApp.HapticFeedback: notificationOccurred('success') на победу, impactOccurred('light') на свайп, selectionChanged() на драг-снап. Только эти три точки — не спамить.
  • Takeover A/B по экспозициям. Арм на сессию: auto (демо играет сразу) vs tap-to-start (постер + кнопка). Метрики: takeover rate, swipe_away(state=autoplay), TTI. Ретеншен по армам НЕ сравниваем — выборка мала.
  • Stories-зона → инбокс челленджей. Хардкод-друзья удаляются. Контент: входящие вызовы (аватар челленджера + «побей 0:41»), мои вызовы со статусами («2/5 друзей прошли»). Пустое состояние: одна карточка-CTA «Брось первый вызов». Тап → лендинг юнита с оверлеем вызова.
  • Challenge v1 — только pins-v1 (декларативные уровни = честный одинаковый конфиг). Merge-вариации подключаются после аудита геймплейного Math.random(). Оверлей вызова: имя + результат + прогресс попыток.

D6 · Инфраструктурные решения

  • Same-origin proxy: Render Static rewrite /api/* → swipe-backend — нет CORS и preflight RTT на каждый батч событий.
  • swipe-backend: отдельный репо, FastAPI + SQLAlchemy/Alembic, Docker на Render; Postgres managed. BOT_TOKEN там же (savePreparedInlineMessage, sendMessage). setWebhook — запрещён (владелец — swipe-bot); проверка в CI grep'ом.
  • Keep-alive с первого дня (Render Cron → /api/health каждые 10 мин); платные инстансы BE+Postgres — решение к началу закрытого теста (сентябрь), не сейчас.
  • startapp: только {c: challenge_id}; смоук-тест лимита длины на реальном iOS/Android клиенте в неделю 2.

Недели

Неделя 1 (7–13 июля) — фундамент: личность, персистентность, телеметрия

  • swipe-backend скелет: репо, Docker, Alembic, схема D1, деплой на Render + Postgres + proxy rewrite + keep-alive.
  • initData: HMAC-валидация (TTL 24ч), POST /session, /results (+ledger level_win), /me, /events.
  • FE: telegram.ts читает initData → Authorization header; звёзды/уровень с сервера (in-memory → серверный баланс, оптимистичный UI); телеметрия-клиент (очередь+батч+sendBeacon) и все события D3.
  • Старый stories-мок скрыт за флагом.
DoD: на реальном iPhone и Android в Telegram: закрыл → открыл — звёзды на месте; события всех типов видны в Postgres; лоадер-метрика пишется.

Неделя 2 (14–20 июля) — петля вызова end-to-end

  • BE: challenges create/get, attempts (+friend_edge, reject self), complete (+двусторонний ledger, идемпотентность), savePreparedInlineMessage, бот-уведомление челленджеру.
  • FE: кнопка «Бросить вызов» на победном экране (pins) → shareMessage / t.me/share фолбэк; deep-link лендинг: start_param → challenge → фид на юнит + оверлей вызова → accept → complete.
  • variants: таблица + ручная заливка спек текущих уровней pins (v1 «генератор» = экспорт из существующего редактора pins).
  • Смоук startapp-лимита на реальных клиентах.
DoD: полный цикл на двух реальных аккаунтах: победил → вызов в чат → друг открыл из чата → сыграл тот же конфиг → обе стороны получили звёзды → челленджеру пришло уведомление с deep-link.

Неделя 3 (21–27 июля) — инбокс, звук, A/B, дашборд

  • Stories-зона = инбокс челленджей (GET /challenges?box=…): входящие, мои со статусами, пустое состояние.
  • Host-джукбокс + 3 семпла + хаптика (D5); юниты шлют sfx-события.
  • Takeover A/B (арм в session, события с ab_arm).
  • Дашборд v1 (/api/stats + одна страница): DAU, D1 по когортам, TTI p50/p95, swipe-away, takeover по армам, share rate, воронка вызова, p95 лоадера.
  • Альфа-смоук: 5–10 своих человек, неделя жизни — первая проверка D1-механики измерения.
DoD: дашборд отвечает на «какой TTI у pins» без ручного SQL; альфа-группа живёт в проде; из инбокса открывается и проходится вызов.
