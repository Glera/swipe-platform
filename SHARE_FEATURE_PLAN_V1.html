1 · Данные, контракты, потоки

1.1 Схема БД (Postgres — источник правды)

Идентификатор игрока везде — telegram_user_id (bigint), берётся ТОЛЬКО из провалидированного initData на бэкенде. Клиент никогда не задаёт свой id.

users

users
  telegram_user_id   bigint      PRIMARY KEY          -- из initData
  username           text        NULL
  first_name         text        NULL
  photo_url          text        NULL
  language_code      text        NULL
  ref_code           text        UNIQUE NOT NULL      -- короткий код игрока (для рефералок/вызовов)
  created_at         timestamptz NOT NULL DEFAULT now()
  last_seen_at       timestamptz NOT NULL DEFAULT now()
  INDEX (ref_code)

friend_edges общий граф друзей

friend_edges                                          -- НЕнаправленное ребро, хранится канонично
  user_low     bigint  NOT NULL  REFERENCES users      -- LEAST(a,b)
  user_high    bigint  NOT NULL  REFERENCES users      -- GREATEST(a,b)
  source       text    NOT NULL                        -- 'challenge' | 'referral' | 'contact'
  first_challenge_id  uuid NULL                         -- чем ребро появилось (аудит)
  created_at   timestamptz NOT NULL DEFAULT now()
  PRIMARY KEY (user_low, user_high)
  INDEX (user_high)                                     -- обратный обход графа
CHECK (user_low < user_high)

Ребро создаётся идемпотентно при принятии вызова (челленджер↔получатель) и в реферальном потоке. «Друзья игрока X» = все рёбра, где X = user_low ИЛИ user_high.

level_results лидерборд · best-per-key

level_results                                          -- ХРАНИМ ТОЛЬКО ЛУЧШИЙ результат по ключу
  user_id       bigint  NOT NULL  REFERENCES users
  mechanic_id   text    NOT NULL                        -- напр. 'pins-v1-swipe'
  level         text    NOT NULL                        -- 'hg' | 'tube' | '1'... (строкой — уровни бывают именованные)
  metric_key    text    NOT NULL                        -- pluggable: 'time_ms' (default) | 'moves' | 'score' ...
  metric_value  numeric NOT NULL                        -- лучшее значение
  lower_is_better boolean NOT NULL DEFAULT true         -- направление метрики (time_ms → true)
  run           jsonb   NULL                            -- опц. детали прохождения (для будущей верификации)
  achieved_at   timestamptz NOT NULL DEFAULT now()
  PRIMARY KEY (user_id, mechanic_id, level, metric_key)
  INDEX (mechanic_id, level, metric_key, metric_value) -- запрос лидерборда

Апдейт по правилу «лучше» (учитывая lower_is_better). Лидерборд = сортировка по metric_value в нужную сторону в рамках (mechanic, level, metric_key). Scope friends = JOIN с friend_edges.

reward_ledger append-only · звёзды

reward_ledger                                          -- append-only, баланс = SUM(delta)
  id            bigserial PRIMARY KEY
  user_id       bigint  NOT NULL  REFERENCES users
  delta         integer NOT NULL                        -- +/- звёзд
  currency      text    NOT NULL DEFAULT 'stars'
  reason        text    NOT NULL                         -- 'challenge_completed_challenger'
                                                         -- 'challenge_completed_recipient'
                                                         -- 'referral_levelup' | 'adjustment'
  challenge_id  uuid    NULL     REFERENCES challenges
  counterparty_id bigint NULL    REFERENCES users        -- вторая сторона (для двусторонней награды)
  idempotency_key text  NOT NULL UNIQUE                  -- напр. f'{challenge_id}:{role}' → нет двойных начислений
  created_at    timestamptz NOT NULL DEFAULT now()
  INDEX (user_id, created_at)

Баланс не денормализуем в v1 (или кэшируем позже в Redis). idempotency_key — единственная защита от двойного начисления (анти-абьюз шире — отложен).

challenges

challenges
  id                    uuid  PRIMARY KEY DEFAULT gen_random_uuid()
  challenger_id         bigint NOT NULL REFERENCES users
  mechanic_id           text   NOT NULL
  level                 text   NOT NULL
  metric_key            text   NOT NULL                  -- по какой метрике вызов
  challenger_value      numeric NOT NULL                 -- результат челленджера (цель «побить»)
  ref_code              text   NOT NULL                  -- реф-код челленджера (в payload)
  startapp_payload      text   NOT NULL                  -- base64url, кладётся в deep-link
  prepared_message_id   text   NULL                      -- от savePreparedInlineMessage
  recipient_id          bigint NULL REFERENCES users     -- кто открыл/принял (заполняется в потоке B)
  recipient_value       numeric NULL                     -- результат получателя
  status                text   NOT NULL DEFAULT 'created'-- created→shared→opened→accepted→completed | expired
  created_at            timestamptz NOT NULL DEFAULT now()
  opened_at             timestamptz NULL
  completed_at          timestamptz NULL
  expires_at            timestamptz NULL                 -- опц. TTL
  INDEX (challenger_id), INDEX (recipient_id), INDEX (status)

Payload вызова (в БД + в deep-link) = {mechanic, level, challenger_id, challenger_name, challenger_value, ref_code}. В startapp кладём КОМПАКТНО (см. 1.3): либо весь payload base64url, либо только challenge_id и добираем через GET /challenges/{id}. Рекомендация: класть challenge_id (короче, меньше подделки), детали — с бэкенда.

1.2 Контракты API — swipe-backend FastAPI

База /api. Все, кроме /health, требуют заголовок Authorization: tma <initData> (сырой initData); бэкенд валидирует HMAC и извлекает user. Ответы JSON. Ошибки: 401 (bad initData), 409 (idемпотентный конфликт), 422 (валидация).

POST /api/results{mechanic_id, level, metric_key, metric_value, run?}{is_best, best_value, rank_friends?, rank_global?}🟩 FE на победе — upsert best
GET /api/leaderboardquery: mechanic_id, level, metric_key, scope=friends|global, limit[{rank, user, metric_value, is_me}]🟩 FE — победный экран / вкладка лидерборда

Серверный вызов Telegram Bot API (не эндпоинт FE): savePreparedInlineMessage(user_id, result=…) → возвращает prepared_message_id. Требует BOT_TOKEN — потому токен живёт на swipe-backend.

1.3 startapp payload (base64url)

deep_link = https://t.me/<bot>/<app>?startapp=<payload>
payload   = base64url(JSON) — компактно, рекомендуется:
            { "c": "<challenge_id>" }              // минимум: только id, детали с бэкенда
   ИЛИ (референс полного контракта payload вызова, если хотим без доп. запроса):
            { "m":"pins-v1-swipe", "l":"tube", "ci":123, "cn":"Аня",
              "cv":41230, "mk":"time_ms", "r":"AB12" }
Ограничение Telegram: startapp ≤ 512 символов, алфавит A-Za-z0-9_-.
Рекомендация v1: класть { "c": challenge_id } → короче и труднее подделать; всё
остальное — из GET /api/challenges/{id} (источник правды — БД).

1.4 Поток A — вызов с победного экрана

  1. FEИгрок выиграл механику+уровень; результат уже отправлен (POST /api/results) и известен лучший.
  2. FEНа победном экране тап «🏆 Бросить вызов».
  3. FE→BEPOST /api/challenges {mechanic_id, level, metric_key, metric_value} (с initData).
  4. BEСоздаёт challenges (status=created), генерит startapp_payload и deep_link.
  5. BE→TGЗовёт savePreparedInlineMessage(challenger_id, result), где result = сообщение вызова: заголовок, template_preview картинка механики + оверлей имени/результата (см. открытый вопрос об оверлее), кнопка с deep_link. Получает prepared_message_id.
  6. BE→FEОтвет {challenge_id, prepared_message_id, deep_link, share_url_fallback}.
  7. FEЕсли Telegram.WebApp.shareMessage есть (8.0) → shareMessage(prepared_message_id) → родной выбор получателя. Иначе фолбэк → openTelegramLink('https://t.me/share/url?url='+deep_link+'&text=…').
  8. FE→BE(опц.) отметить status→shared.

1.5 Поток B — друг открывает deep-link → лендинг → двусторонняя награда

  1. TGДруг жмёт кнопку в присланном сообщении → открывает t.me/<bot>/<app>?startapp=<payload>.
  2. FEMini App стартует; читает Telegram.WebApp.initDataUnsafe.start_param (он же tgWebAppStartParam) → base64url-decode → challenge_id.
  3. FE→BEPOST /api/session (initData) → user; затем GET /api/challenges/{id} → контекст (механика, уровень, имя+результат челленджера, template_preview).
  4. FEЛендит игрока СРАЗУ на нужную механику/уровень фида (deep-link во внутренний индекс + уровень), показывает оверлей вызова: «Аня прошла за 0:41 — побей!».
  5. FE→BEPOST /api/challenges/{id}/accept → 🟦 пишет recipient_id, создаёт friend_edge(challenger, recipient, source='challenge'), status→accepted (идемпотентно).
  6. FEДруг проходит уровень.
  7. FE→BEPOST /api/challenges/{id}/complete {metric_key, metric_value}.
  8. BEРезолв исхода (побил ли результат челленджера), апдейт level_results, запись двух строк reward_ledger (получателю и челленджеру) идемпотентно по challenge_id:role, status→completed. Возврат наград.
  9. FEПоказывает начисленные звёзды обеим сторонам (челленджеру — при следующем заходе/через баланс).

Двусторонность: правило наград — конфигурируемое (напр. фикс. челленджеру за принятый+завершённый вызов, получателю — за прохождение, бонус за «побил»). Логика целиком на BE; FE только отображает результат.

1.6 Поток auth (initData)

  1. FEЧитает window.Telegram.WebApp.initData (сырая строка) при старте.
  2. FE→BEШлёт её в заголовке Authorization: tma <initData> с каждым запросом (или обменивает на короткоживущий session-JWT — опц. в v1).
  3. BEВалидирует по спецификации Telegram: secret = HMAC_SHA256("WebAppData", BOT_TOKEN); hash == HMAC_SHA256(secret, data_check_string); проверка свежести auth_date (TTL). Извлекает user.id/first_name/username/photo_url. Только это — доверенный источник личности.

1.7 Поток результата/лидерборда

  1. FE→BEНа победе POST /api/results — upsert best по (user, mechanic, level, metric_key) с учётом направления метрики.
  2. FE→BEПобедный экран/вкладка → GET /api/leaderboard?scope=friends (дефолт) → рейтинг.
  3. BEМетрика pluggable: столбец metric_key + lower_is_better; дефолт time_ms (меньше = лучше). Друзья = через friend_edges.

2 · FE vs BE — разграничение

🟩 Frontend — feed-prototype

Тонкий клиент. Никаких секретов, никаких решений о доверии/наградах.

  • telegram.ts: читать initData; прокидывать в BE; читать start_param.
  • Декодить startapp payload → лендить фид на нужную механику/уровень (внутренний роутинг по индексу манифеста + уровню).
  • Победный экран: кнопка «Бросить вызов» → POST /challenges → shareMessage(prepared_id) / фолбэк t.me/share/url.
  • Рендер оверлея вызова (имя+результат челленджера) и превью-шаблона в приложении (canvas/DOM).
  • Слать POST /results, /challenges/{id}/accept, /complete; рендерить лидерборд и баланс.
  • Фичефлаг: если не в Telegram (обычный браузер / AppLovin) — вся фича no-op (как сейчас telegram.ts).

🟦 Backend — swipe-backend

Граница доверия и вся запись. Postgres — источник правды.

  • Валидация initData HMAC (личность игрока). Держит BOT_TOKEN.
  • Все записи: upsert best (level_results), reward_ledger, friend_edges, challenges.
  • savePreparedInlineMessage (серверный вызов Bot API) — выпуск prepared-сообщений.
  • Резолв двусторонней награды + идемпотентность (idempotency_key).
  • Запросы лидерборда (scope friends/global, направление метрики).
  • Реферальный модуль: рёбра графа + левелап-награды (отдельный поток).
  • (v1) template_preview_url: см. открытый вопрос — статичная картинка на механику vs динамический оверлей.

4 · Инфра / механика (в конец)

4.1 Render — сервисы

Текущее:
  swipe-platform   Static Site   (feed + <id>.html)          repo Glera/swipe-platform
  swipe-bot        Web (Docker)  (launcher + webhook owner)    repo Glera/swipe-bot

Добавляем:
  swipe-backend    Web Service (Docker, FastAPI/uvicorn)       repo Glera/swipe-backend (новый)
  Render Postgres  managed DB (источник правды)                → DATABASE_URL в swipe-backend

Отдельный репозиторий (чистое разделение от бота). render.yaml по образцу swipe-bot: type: web, runtime: docker, plan. Persistent-диск НЕ нужен (состояние в Postgres) — важно, т.к. на free-плане ФС эфемерна.

4.2 Env (swipe-backend)

BOT_TOKEN          secret   — для валидации initData + savePreparedInlineMessage
DATABASE_URL       secret   — из Render Postgres
ALLOWED_ORIGINS    value    — https://swipe-platform.onrender.com (+ tg web origins)
INITDATA_MAX_AGE   value    — TTL auth_date, напр. 86400
BOT_USERNAME/APP   value    — для сборки deep-link t.me/<bot>/<app>
PUBLIC_BASE_URL    value    — свой URL (для template_preview, health)

4.3 CORS

Mini App отдаётся с swipe-platform.onrender.com, а API — на другом origin (swipe-backend…) → нужен CORS allowlist (ALLOWED_ORIGINS), методы GET/POST, заголовок Authorization. Альтернатива (позже) — проксировать /api через статику, чтобы был same-origin.

4.4 Миграции

Alembic (SQLAlchemy) или простой SQL-раннер. Запуск на деплое (Render preDeploy/release command) или на старте до приёма трафика. Хранить версии в репо swipe-backend.

4.5 Cold-start / keep-alive

Free Render засыпает при простое (первый /start после сна уже лагает — отмечено в README бота). Для потока «открыл вызов» холодный старт критичен. Меры: keep-alive пинг GET /api/health (Render Cron / внешний аптайм-пингер) или платный инстанс на проде. Postgres free-tier ограничен/истекает — заложить переход на платный до запуска.

4.6 Идемпотентность и порядок внедрения

  • Идемпотентность наград: reward_ledger.idempotency_key = f"{challenge_id}:{role}" UNIQUE. Повтор /complete не задваивает.
  • Порядок внедрения (предлагаемый): (1) swipe-backend скелет + Postgres + initData-auth + /session; (2) /results+/leaderboard; (3) /challenges+savePreparedInlineMessage+shareMessage; (4) deep-link лендинг + accept/complete + ledger; (5) реф-модуль.

4.7 Риски

Cold start на free-плане ломает UX открытия вызова (лаг несколько секунд). → keep-alive/платный инстанс.
Postgres free-tier ограничен по объёму/времени жизни. → бюджет на платный тариф до запуска.
prepared inline message — короткоживущий/одноразовый; выпускать по требованию в момент шеринга, не пакетно. Возможны ограничения на типы контента/доступность получателя.
Анти-абьюз отложен → самовызовы, повторные фарм-циклы, накрутка лидерборда возможны в v1. Осознанно; ledger/идемпотентность лишь частично сдерживают.
initData сейчас не шлётся фидом — net-new и на FE, и на BE; без него нет доверенной личности.
Единый webhook: если swipe-backend случайно вызовет setWebhook — перехватит апдейты у swipe-bot. Явно запретить.

4.8 Открытые вопросы

Template preview с оверлеем имени/результата для ШАРИМОГО сообщения. Внутри приложения оверлей легко рисуется (canvas/DOM). Но картинка в prepared inline message — это публичный URL.
